## 总纲（一句话）

**你看到的"五六十 G"不是泄漏，是模型本体在内存里的正常驻留。绝大多数"省内存"旋钮只削峰值、
不削常驻；其中「TE 后卸载」这个开关在排查当时是彻底失效的（调了一个 ComfyUI 里不存在的函数名，
异常被静默吞掉）—— 该 bug 已于 2026-10-13 修复，修复后它是否真能降常驻尚待实测，
见下文 Q4/Q6 与文末修复章节。**

## 名词速查

| 词 | 人话 |
|---|---|
| 权重 | 模型的"大脑本体"，就是那几十 GB 的数字 |
| 张量 | 一堆排好队的数字（可以是一张图、一段声音） |
| 激活 | 计算到一半的中间结果，用完就该扔 |
| latent | 画面被压缩后的样子（浓缩液，不是像素） |
| cond / 条件 | 提示词翻译成的数字指令，用来指挥模型画什么 |
| 采样 / 去噪 | 从一堆雪花噪点开始，一步步洗出画面 |
| TE | 文本编码器（Text Encoder），把文字翻成条件的大模型 |
| UNET / 主模型 | 真正"画画"的那个大模型 |
| VAE | 把浓缩液还原成像素（或反过来）的小一点的模型 |
| 常驻 | 一直占着不放的那部分（地板） |
| 峰值 | 某一瞬间冲上去的最高点（天花板） |
| 显存 VRAM | 显卡上的高速内存，小、快 |
| 内存 RAM | 主板上的内存条，大、慢一点 |
| 卸载 offload | ComfyUI 语境下 = 从显卡搬回内存，**不是**从内存删掉 |

## 设备分工：四个池子

```
┌─ 电脑主机 ──────────────┐        ┌─ 显卡 ────────────────┐
│  CPU：调度、读文件、压 mp4 │  PCIe │  GPU：只擅长矩阵乘法      │
│  内存 RAM（几十 GB）      │◄─────►│  显存 VRAM（几~几十 GB）  │
│   · 模型权重的家          │  通道  │   · 正在算的那几层权重    │
│   · 成片帧、参考素材      │        │   · 中间结果（激活）      │
└─────────────────────────┘        └──────────────────────┘
```

权重必须先从内存搬到显存才能算；搬一次要花时间，来回搬是最贵的开销。

## Q1 / Q2：H3 推理运行的原理，各设备怎么运作

一次生成分四站，每站都要"背"着不同的模型权重：

| 站 | 干什么 | 背着谁 |
|---|---|---|
| ① 文本编码 | 文字 → 条件 | TE 权重 |
| ② 去噪采样 | 噪点 → 画面（在 latent 空间） | 主模型权重 |
| ③ 解码成图 | 浓缩液 → 像素 | VAE 权重 |
| ④ 压制成片 | 帧序列 → mp4 | CPU 编码（不怎么用显卡） |

- **一采**：② → ③ 走一遍，出基础分辨率的片。
- **二采**：把基础片放大，再走一遍 ② → ③，最后 ④。所以整套权重要"背"第二遍。

设备分工：CPU 负责调度、读模型文件、压 mp4；GPU 只干矩阵乘法，必须先把权重从内存搬上显存；
显存放"正在算的那几层权重 + 中间结果"；内存放"权重的完整副本 + 成片帧 + 参考素材 + Python 本身"。

## Q3：TE 编码完、主模型采样完"该卸载"了，为什么解码时还有五六十 G

因为**ComfyUI 的"卸载" = 把权重从显卡搬回内存，不是从内存里删掉**。

```
磁盘（模型文件，几十 GB，冷数据，几乎不再读第二遍）
   │ ① 加载：读进内存（几十秒，只干一次）
   ▼
内存 RAM  ← 你看到的五六十 G 基本都在这里
   │ ② 换入：搬上显卡（毫秒级，反复发生）
   ▼        ③ 所谓「卸载」：只回到这里（内存占用纹丝不动）
显存 VRAM
   ④ 写回磁盘：几乎从不发生
```

文件被读进内存后，只要 Python 里还有人握着那个模型对象，它就一直在。
真正让它消失的唯一办法是**销毁对象**（没人引用 + 垃圾回收）。

`unload_model_and_clones` 会走 `free_memory(1e30, device, keep_loaded)`，

所以它对"内存占用"这个指标**没有帮助**。它真正能动的是：

- 显存：把 TE 的分页窗口/权重请出显卡，给采样与解码腾地方；
- 项目实测过的那个场景（64GB 无 swap 云端跑 1MP，段间残留 +2G/段，
  第 3–4 段必撞 cgroup 上限被**整个容器**杀掉，见 `tests/test_te_drop.py` 文件头背景）
  —— ⚠ 这条当初是立项理由，但**已被下面的实测推翻**：内存不降就救不了内存侧。

> ✅ **2026-10-13 实测结论：它不省内存，内存占用无变化。**
>
> 面板提示 / `perf.py` / `docs/改动总结_…_2026-10-12.md` 原先都写着
> **「单段峰值 59.5G/64G → ~35G」** —— 那个数字**是错的，已全部删除**。两条原因：
>
> 1. **开关当时根本没在工作**：它在 2026-10-13 之前一直是静默空转的
>    （原实现调了 ComfyUI 里不存在的 `unload_model_and_clips`，异常被吞，见上文 Q4/Q6），
>    所以 2026-09-30 那次云端会话**不可能**测出"开了它之后降到 35G" ——
>    那时开与不开行为逐字相同。且 `59.5 − 25.9 = 33.6 ≈ 35`，形似减法而非实测。
> 2. **修好之后它也只动显存**：`for_dynamic=False` → `LoadedModel.model_unload(1e30)`
>    → `ModelPatcher.detach(unpatch_weights=True)`，做的是
>    `model_patches_to(offload_device)`（权重从显存搬回主机）+ 从
>    `current_loaded_models` 摘掉 + `soft_empty_cache()`。
>    **ComfyUI 的「卸载」= 从显存搬回内存，不是从内存删掉** ——
>    那 25.9GB 权重副本该在还在，内存地板一点不动（原本驻显存的话，搬回内存后 RSS 反而涨）。
>
> **它到底有什么用**：给小显存卡腾显存窗口；代价是每段首次编码多一次回载 + 重 patch（约 45s）。
> 默认值现在仍是强制开（2026-10-12 拍板），但**当初的理由已经不成立**，要不要改回
> `auto` 需要重新判断 —— 这是用户的决定，不是文档能替的。

## Q5：ComfyUI 为什么不把模型卸载到磁盘

1. **回磁盘代价太大。** 20–40GB 从 NVMe 读回来是几十秒级（项目实测一次回载约 45 秒）；
   留内存里换入是毫秒级。
2. **开启动态显存（aimdo）时，内存里那份不是"缓存"，是权重的家。**
   显卡只是开了一扇窗（vbar）去看它，用到哪层才搬哪层。把家拆了就必须回磁盘重读。
   所以"留在内存"不是偷懒，是这套机制的**前提条件**。

补充：真正把主机内存里那几份副本吐出来的函数是
`ModelPatcherDynamic.partially_unload_ram()`（`comfy/model_patcher.py:2105`），
它只由两处触发——`unpin_all_weights()`（patcher 被回收时）和内存压力下的
`extra_ram_release()`。也就是说：**只有在内存真的不够、或对象真的被销毁时才会还内存。**

## Q7：Staged / 内存副本 / 没人引用的中间张量

### 「显存 staged 块」/ Staged

日志里 `21603MB Staged` 出自 `comfy/model_patcher.py:2032`，原文是
*"Model X prepared for dynamic VRAM loading. NMB Staged."*

翻译：**"已经摆好、随时可搬上显卡的权重量"**，不是已经吃掉的显存。
它其实就是在告诉你"这份东西有多大"。

### 「内存副本」

动态模式下主机内存里可能同时躺着好几份（见 `comfy/model_patcher.py:2105` 的 subsets 名单）：

| subset | 是什么 |
|---|---|
| `weights` | 原始权重 |
| `weights-loaded` | 按目标精度转换后的副本 |
| `weights-fast` | 快速盘副本 |
| `patches` / `patches-loaded` / `patches-fast` | LoRA 补丁 |

所以你算"模型 21GB"，实际内存里可能是 21GB 的倍数。

### 「没人引用的中间张量」

算完就没人再用的临时数字。Python 和 torch 都不会立刻还给系统
（torch 的缓存分配器会先扣在手里当备用），要 `gc.collect()` + 回收才吐出来。
属于"该扔没扔"，量不大，但会让底部缓慢爬升。

## Q8：都卸载了，cond 缓存为什么还能命中

**这两样东西根本不在一层。**

- 缓存里存的是**产物**：提示词翻出来的那串数字（cond）。
- 卸载扔掉的是**工具**：模型权重（TE 的大脑）。

大脑下班了，翻译稿还在抽屉里，下次直接拿。所以命中 → 连 TE 都不用加载 → 比"卸载"更省。

也因此，插件的实现只在**没命中**时才去丢 TE（`cond_cache.py:202-204`）——
命中时压根没碰过 TE 权重，丢了纯属白付一次回载。这个设计是对的，只是 Q4 那个函数名把它废了。

**命中边界**（`cond_cache.py` 文件头）：只有**不挂首帧图、不挂参考素材**的段才能命中
（独立镜头、续拍段）。挂了图的会主动跳过——因为一采与二采画幅不同、视觉 token 数不同，
cond 本来就不一样，强行复用才是 bug。

## Q9 / Q10：pinned 锁页内存 vs NVMe

**锁页内存（pinned）**：向操作系统申请"这几 GB 物理内存不许被换出到磁盘、也不许搬家"。
好处是显卡可以直接用 DMA 去内存里抓数据，不用 CPU 中转，快很多；
代价是**它实打实占着物理内存条，谁也动不了**。

预算来自 `comfy/model_management.py:1631-1634`（v0.38.2 复核；旧文记的
1613-1621 是更早版本的行号）：

- Windows：`MAX_PINNED_MEMORY = 内存 × 40%`（注释：Windows 上限约 50%）
- Linux：`max(内存×40%, min(内存×90%, 内存−4GB, 内存+swap−16GB))`

| | 去 pinned 内存 | 去 NVMe |
|---|---|---|
| 内存占用 | 占着，且不可换出 | 几乎不占（只有缓存页） |
| 换入速度 | 快，DMA 直取 | 慢，要重读文件 |
| 什么时候吃亏 | 内存紧张时它不让路 | 每次换入都慢 |
| 本质 | 用内存换速度 | 用时间换内存 |

**你的怀疑方向是对的**：动态显存模式下，权重正是被"钉"在主机内存（vbar 后备区）里的，
其中一部分就是 pinned。它不是"去了别的地方"，它压根就没离开内存。

## Q11 / Q12：段间残留量基本一致，且随模型而变

### 残留曲线

```
80 ┤
   ┤                                        ┈┈ 容器上限 64GB
60 ┤        ●              ●              ●
   ┤   ●         ●    ●         ●    ●         ●
40 ┤━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 地板线 ≈ 模型权重本体
   └────────────────────────────────────────────
        段1          段2          段3
```

每段冲高，然后**回落到同一条地板线**。

### 你的判断是对的

- 残留量随更换模型而变 → 地板 = 模型体积；
- 换 bf16 主模型后内存大增、第二段解码时断连 → bf16 每参数 2 字节、fp8 只要 1 字节，
  地板直接抬高约一倍，天花板撞上容器上限。

**别再往"泄漏"方向找了。** 唯一需要注意的是地板有极缓慢的爬升（实测约 +2G/段），
那是"该扔没扔的中间张量"和缓存累积，量级远小于模型本体。

## Q13：那一堆省内存机制到底有没有发挥作用

### 关键区别：峰值 vs 常驻

```
80 ┤
   ┤         ╱▔▔╲                      ← 不分块的尖峰
60 ┤        ╱    ╲
   ┤   ╌╌╌╌╱      ╲╌╌╌╌                ← 分块后的尖峰（被压平）
40 ┤━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ← 常驻地板（纹丝不动）
   └──────────────────────────────────
```

分块类手段只压低上半部分，地板高度不变。

### 逐条点名

> ⚠ 下表是**排查当时的判定**（2026-10-13 凌晨）。`te_drop_after_cond` 那一行已过时，
> 见行内标注。

| 机制 | 它实际做的事 | 对"内存常驻" |
|---|---|---|
| **te_drop_after_cond** | 想只卸 TE | ⚠️ **当时彻底失效**（函数名不存在，异常被吞）→ **2026-10-13 已修复**；但**实测不降常驻**（卸载=从显存搬回内存，不是删）—— 它只腾显存 |
| cond 文本编码缓存 | 相同提示词复用编码结果 | ⚠️ 只省时间不省内存；挂首帧/参考图会跳过 |
| blocks_to_swap / vram_reserve_gb | 调 aimdo 显存预留，逼权重页换出 | ✅ 真实生效，但**只管显存**；换出的页还在内存，内存可能更高 |
| blocks_prefetch | 官方预取队列开关 | ⚠️ 只影响速度 |
| ff_chunk / attn_head / 时序 / 空间 tile 分块 | 把一次大计算切成小块 | ✅ **削峰值有效**，❌ 对地板无效 |
| vram_shuffle | 精化前腾挪 | ❌ 只动显存 |
| frames_dtype / final_mode | 成片帧精度与合成方式 | ✅ 对"成片帧"这部分内存有效 |
| offload_guard_ratio / guard_action | 落盘前告警或拦截 | ❌ 它是仪表盘，不是省内存的 |
| keep_upscaler_resident | 放大网络常驻 | ❌ 反向，增加常驻 |
| oom_autoretry | OOM 后重试兜底 | ❌ 事后补救，不减占用 |

### 真正能降地板的三条路

1. **换更小的模型 / 更低精度**（你已经试过，方向对）。
2. **让成片帧不堆在内存里**（`final_mode` / `frames_dtype`）。
3. **段与段之间把模型对象真的销毁掉**——不是"卸载"，是删引用 + 垃圾回收。
   代价：下一段多付几十秒回载。这是唯一能动地板的软件手段，但它是拿时间换内存。

> ✅ 2026-10-13 实测：修好之后的 `te_drop_after_cond` **不能**成为第 4 条路 ——
> 它不释放那 25.9GB 权重副本（ComfyUI 的「卸载」只是从显存搬回内存）。
> 上面三条维持不变。

## 二、为什么第二段炸，而且偏偏是在"解码"

### 1. 解码是整条链的 RAM 峰值点 —— 这是物理决定的

latent 是压缩的，像素帧是展开的。**解码是唯一把"浓缩液"还原成"全尺寸像素"的步骤。**

粗算：1080p 单帧 fp32 = 1920×1080×3×4B ≈ 24.9MB；10 秒 @24fps = 240 帧 ≈ **6GB**。
二采的高清分辨率更大，还要再乘一个系数。采样期从不产生这个量级。

### 2. 第二段才炸 = 地板抬了

```
80 ┤
   ┤                                    ┈┈┈┈ 容器上限
   ┤      ╱╲          ●              ╱╲
60 ┤     ╱  ╲        ╱  ╲          ╱    ╲
   ┤    ╱    ╲      ╱    ╲        ╱      ╲
40 ┤━━━╱──────╲────╱──────╲──────╱────────╲──
   └──────────────────────────────────────────
       段1 解码    段2 解码     段3 解码
        ↑ 差一口气  ↑ 撞顶，容器被杀
   （地板：模型本体 + 段间残留，每段 +2GB）
```

三段各自多出来的那坨（解码帧）**一样大**，但地板在抬 —— 所以飞过去的只有后面那些段。

**不是第二段有什么特别，而是第二段是第一个"带着前一段垃圾上路"的。**

`tests/test_te_drop.py` 文件头写着实测实况：64GB 无 swap 云端跑 1MP，
**段间残留 +2G/段**。三个来源：

| 来源 | 出处 |
|---|---|
| 模型本体从不卸载（只从显卡搬回内存） | ComfyUI `free_memory()` 语义 |
| `prev_tail_frame` / `prev_tail_clip`（上段末 24 帧，CPU） | `nodes.py:4332-4333` |
| torch CPU 缓存分配器：帧释放了但 RSS 不还给系统 | torch 行为 |

bf16 把地板整体抬了一大截 → 段1 差一口气过了，段2 就撞。

### 3. 真的有"额外显存占用"，而且 ComfyUI 自己看不见

`_comfy_exec_cleanup()` 的 docstring（`nodes.py:581-589`）里写死了三样：

| ① | `model_prefetch` 的 CUDA 图（`module._comfy_graph`） | 既不计入 torch 分配器、也不计入 `current_loaded_models`；`torch.cuda.empty_cache()` **完全无效** |
|---|---|---|
| ② | cast buffer / 脏 mmap / cross-step state | 同上，`reset_cast_buffers()` 才能收 |
| ③ | VBAR 的 watermark limit | 按上一段的压力调过，不重置就一直按旧压力驱逐页 |

**根子**：导演台多段是"**一次**节点执行跑完 N 段"，而 ComfyUI 这套清理挂在
"节点执行结束"上 —— 于是**段间从不发生**（`nodes.py:578` 原话）。

插件在 2026-10-08 已补 `_segment_end_cleanup()`，每段末调用（`nodes.py:4528`），
解码前还补了一次（`nodes.py:3650`）。
**如果你的插件版本早于这个改动，第二段必然带着第一段的这三样一起跑。**

### 4. 为什么 bf16 主模型"装得上"，跑起来却不够 —— 两笔不同的钱

**权重是 mmap 读进来的**（`comfy/utils.py:190` `torch_args["mmap"] = True`；
aimdo 另有 `comfy_aimdo.model_mmap.ModelMMAP`）。

这意味着权重的那些页是**文件页**：内存紧张时操作系统可以悄悄丢掉，下次缺页再读回来，
**不会杀进程**。所以你看到"40GB 的模型装进去了"——其实那是可以被挤掉的部分。

真正不可丢弃的是**匿名页**：解码出来的帧、torch 缓存、pinned 锁页内存。

> "模型装得上"与"跑到一半够不够"是两笔完全不同的钱。
> Linux 无 swap + cgroup 上限下，匿名页 + 文件页一起撞上限 → **整个容器被杀**
> ——你看到的就是"断连"。

## 三、当下真正有效的手段（按收益排序）

1. **★ 用「逐段确认」审片模式** —— 这是目前唯一能让"系统级段间清理"真正发生的办法。
   `nodes.py:578` 原话：*"手动逐段跑则每段各是一次执行、每段都清一次。这正是
   「手动逐段 + 点一下清理就正常」的真正机制。"*
2. **别跑二采**（或只给关键段开）：二采是更大画布再走一遍采样 + 解码，峰值几乎翻倍。
3. **把段切短**：帧数线性决定解码峰值。10s → 5s 直接砍一半。
4. **`final_mode` 保持默认**（auto/stream）：千万别设 `memory`，那会让全链帧全堆在内存里。

### ★★ 顺手又查出一个"看着有用其实不对症"的旋钮：`frames_dtype`

`_frames_uint8` 只作用在 `all_frames` 那一份上（`nodes.py:3756` / `4328`），
而 `all_frames` **只在 `final_mode=memory` 时才非空**（`nodes.py:1387`）
→ 默认流式口径下它是空的。

**真正送去编码的 `frames` 始终是 float32。**

结论：**`frames_dtype=uint8` 省的是"累积那一份"，不是"峰值那一份"。**
默认口径下这个键几乎无效。

# 追加（2026-10-13 第三轮）：★ 找到真根因 + 已实现 `decode_ram_guard`

## 一、★★ 真根因：解码是一张「固定开口支票」

**H3 视频 VAE 会在「开始解码之前」把整段视频的完整像素缓冲一次性预分配到主机内存。**

两处都会这么做（都是 ComfyUI 官方代码，不是插件的行为）：

| 位置 | 行为 |
|---|---|
| `comfy/sd.py:1281-1286` | 对声明了 `comfy_has_chunked_io` 的 VAE（H3 有，见 `comfy/ldm/minimax/vae.py:410`），先 `pixel_samples = torch.empty(first_stage_model.decode_output_shape(...), device=self.output_device, dtype=self.vae_output_dtype())`，再逐块往里填 |
| `comfy/ldm/minimax/vae.py:713` | VAE 自己的兜底路径同样全量预分配，注释写得很直白：*"finalized chunks stream out of VRAM so the full video never sits on the GPU"* |

⚠ 上表行号已按本机 **v0.38.2** 复核（原文记的 `sd.py:1270-1277` / `vae.py:408` / `vae.py:708-711`
是旧版本的行号，已漂移）。行号会随 ComfyUI 版本变，**引用时请按符号名核对**。

而 `decode_output_shape` = `(b, 3, frames, h×ratio, w×ratio)`（`vae.py:488`），
所以这张支票的面额 = **帧数 × 高 × 宽 × 3 × 4 字节**：

| 场景 | 面额 |
|---|---|
| 1080p，5 秒 @24fps（120 帧） | ≈ 2.8 GB |
| 1080p，10 秒 @24fps（240 帧） | ≈ 5.6 GB（含 15% 余量 ≈ 6.4 GB） |
| 二采高清 | 按分辨率再乘一个系数 |

**它有两个要命的性质：**

1. **一开始就要全额，中途不可能收回** —— 所以任何"事后再回收"的措施都救不到这一刻。
2. **与显存状态、卸载开关完全无关** —— 显存再干净也省不掉它。

这完美解释了你的观察：**模型常驻已经吃掉 ~95% 内存，剩下那一点点余量，正好被这张几 GB 的支票顶穿。**

## 二、★ 为什么现有所有兜底都救不到

**它们的集体缺陷：治的全是显存（VRAM），没有一条治内存（RAM）。**

| 机制 | 出处 | 治什么 |
|---|---|---|
| `_comfy_exec_cleanup` | `nodes.py:573` | 显存（CUDA 图 / cast buffer / VBAR watermark） |
| `_reclaim_orphan_vram` | `nodes.py:519` | 显存（无主块） |
| `_segment_end_cleanup` | `nodes.py:614` | 显存 |
| `unload_model_and_clones` | `upscale.py:3001` / `nodes.py:3570` | 显存 |
| `offload_guard` | `perf.py:413` | 只读告警，不改行为 |
| `oom_retry` | `nodes.py:3662` | **显存** OOM 异常后重试 |

**每一条单独看都写得挺合理 —— 但集体对这个病症无效。**

更致命的一条：**Linux 无 swap / cgroup 下内存不够是 `SIGKILL`，连异常都不抛。**
而 `oom_retry` 那套是"抛了再救"的 —— 对 RAM 完全用不上。
所以你看到的从来不是报错，而是**无声断连 + 运行记录消失**。

> 一句话：**显存不够是"抛异常"，可以救；内存不够是"枪毙"，救不了。**
> 而你这个病正好长在内存上。

## 三、已实现：`decode_ram_guard`（契合"不要白付代价"）

你的要求是"**只在必要的时候才动，不要为了省内存把生成拖慢**"。
所以判据用**预测需求**，而不是"定期清理"或"历史残留到阈值就收"：

| 情况 | 动作 | 代价 |
|---|---|---|
| 可用 − 需求 ≥ 1GB | **什么都不做** | 一次 meminfo 读，微秒级 |
| 理论够但余量 < 1GB | `tight`，只打一行提示 | 同上 |
| **预测真不够** + `auto` | `gc.collect()` + `malloc_trim()` + **复测**并如实报告 | 毫秒级，不动任何在用张量 |
| `warn` | 永不改行为，只报 | 微秒级 |
| `off` | 连 meminfo 都不读 | 零 |

**`malloc_trim` 是关键**：glibc / torch 释放了内存**不会主动还给内核**，进程 RSS 停在历史最高点 —— 这正是实测到的"段间残留 +2G/段"的大头（另一部分是模型本体，那部分本来就不该降）。Linux 上 `malloc_trim(0)` 把空闲堆交回内核，RSS 立刻下降。Windows 由 pagefile 兜底，直接跳过。

接线点：**全仓只有两处视频解码**（基础解码 `nodes.py`、高清解码 `upscale.py:3011`），两处都在 `_comfy_exec_cleanup` 之后、`oom_retry` 之前插好了。

新增 `tests/test_decode_ram_guard.py`（10 项），专门钉死"**够用时零动作**"这条硬要求。

# 追加（2026-10-13 第四轮）：时间分块解码已落地（默认关）

## 新文件 `vae_chunk.py`

把那张一次性开口支票拆成分期付款：**沿时间把 latent 切成 K 段，每段单独调一次
`video_vae.decode()`**，每次的预分配缓冲只有 1/K。

### ★ 安全契约：账对不上就**不分块**

帧数是这类改动**唯一真正致命**的失败模式（错了 → 音画不同步、段长漂移、成片错位）。
所以流程是**先算账再动手**：

1. 用 VAE 自己的公式（`decode_output_shape` / `_decode_temporal_frame_plan` 的整数版
   复刻）算出「整段解出多少帧」和「每段各解出多少帧」；
2. **只有** `sum(每段帧数) == 整段帧数` 才允许分块；
3. 对不上 → 返回 `ok=False`，调用方照旧走一次完整 `decode()`。

**要么它算得完全正确，要么它的行为与没装它时逐字相同。**

### 接缝的真相（如实写，别吹）

**当时的推理**：VAE 内部每个时序块都会**丢弃开头 `frame_pre_padding` 帧**（H3 实际
`vae_ratio_t=4`、`clip_length=17` → `frame_pre_padding = (-17)%4 = 3`）。
把 latent 切开后，**每一段各自**都要丢开头 3 帧 → 拼接处的**内容**会跳 3 帧
（约 0.125 秒）。帧数对得上，内容不连续。

`vae_decode_blend`（默认 0）可以把硬跳变成几帧的短斜坡 —— 实现上是**原地替换
prev 的尾帧**，两个张量的帧数都不变（任何丢弃帧的溶解都会破坏账目等式）。
**它只是柔化，没有消除跳跃。** 真正无缝需要在 latent 上重叠解码，而那会让帧数
对不上（实测重叠 1 token 就差 1 帧），会被账目校验直接拒绝 —— 这是官方 VAE 的
结构决定的。

> ✅ **2026-10-13 真机实测：上面「跳 3 帧」这个结论没有复现，是错的。**
>
> 用真实 `minimax_h3_video_vae_fp16.safetensors`（`MiniMaxH3VideoVAE`）在
> T_lat=30、每块上限 15 token（切成 2 段 × 51 帧）下对比：
> `decode_chunked` 与整段 `vae.decode()` 的输出**形状完全一致**（`[1,102,128,128,3]`），
> **逐帧平均绝对差中位数 = 0，102 帧里 0 帧差异 > 0.05**，最大差异仅 0.011～0.037
> 且局限在接缝附近。**不存在 3 帧的内容跳跃。**
>
> 原因：`plan()` 只允许「账目对得上」的切法，而这类切法的切点**天然落在
> 官方内部时序块边界上**（段长向 `tokens_chunk_size` 的整数倍对齐），于是每段的
> 内部块划分与整段解码**逐块重合**，那 3 帧的丢弃在两边是同一件事，不产生相对位移。
> 原始推理漏掉的就是这一点：`frames_for` 已经把每块丢弃的帧数算进去了。
>
> 结论：`vae_decode_blend` 因此更像**保险**而非必需（默认 0 即可）。

### ⛔ 同一轮实测还挖出一个真 bug：分块解码**从未真正生效**

`decode_chunked` 原先按 **dim=2** 拼接，并注释说「两种形态的时间维都在 dim=2」——
**这是错的**。真实 `vae.decode()` 返回的是 **[B, T, H, W, C]**，时间在 **dim=1**：

```python
# comfy/sd.py，VAE.decode 的最后一行（v0.38.2 在 1354 行）
pixel_samples = pixel_samples.to(self.output_device).movedim(1,-1)
```

`decode_output_shape` 给的 `(b, 3, frames, h, w)` 是**内部**缓冲的布局
（`first_stage_model.decode` 往里写的那块），跟这个包装函数吐出来的不是同一个。

后果：dim=2 是**高度**，于是两段沿高度拼成 `(1, 51, 256, 128, 3)` →
帧数校验拿到 256 ≠ 102 → 抛异常 → 调用方安静退回整段解码。
**也就是说：这个功能从上线起就一次都没成功过**，而且因为回退是"安静"的
（只在日志里一行），从面板上完全看不出来。

为什么单测没发现：`tests/test_vae_chunk.py` 里的假 VAE 用的是
**[B, C, T, H, W]**（把错误布局当成了契约），而真正危险的 `decode_chunked`
**一个用例都没有**。

修复：新增 `_time_dim()`，按「哪一维等于本段应得帧数」**实测定位**时间维
（不写死维号）；`_blend_join` 也改成按 dim 参数操作。并补了 5 个用例，
其中包含**真实布局**的假 VAE 和一个「换回内部布局也要能拼对」的反例。

### 新增 perf 键（默认关）

### 数值实测（H3 真实参数，帧数账目全部对上）
