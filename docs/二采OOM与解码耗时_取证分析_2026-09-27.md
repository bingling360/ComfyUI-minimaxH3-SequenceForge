## 2. 问题一：选了「注意力分块」，为什么实际没开？

### 2.1 报告里的说法

```
性能：注意力头分块未启用（注意力头分块自测不通过（attn.forward 里含跨 head 操作，
      不是纯分组可分离）——本次不装，输出保持原样）
```

来源 `upscale.py:2477-2479`。也就是说：**节点主动拒装**，不是没生效。

### 2.2 但这个原因是错的 —— 探针自己写错了输入维度

`upscale.py:2274-2306` 的 `_attn_head_selfcheck`：

```python
s = 8
x = torch.randn((s, heads * head_dim), device=dev, dtype=torch.float32)   # ← line 2295
with torch.no_grad():
    full    = _attn_forward_reference(attn, x, None)      # 调真 attn(x)
    chunked = _attn_forward_chunked(attn, x, None, n_chunks)
```

这里造输入用的是 **`heads * head_dim`**，而 `qkv_proj` 期待的是 **`hidden`**。
H3 主干：`hidden=5376`、`heads=56`、`head_dim=128` → `56 × 128 = 7168 ≠ 5376`。

**实测复现**（真 `comfy.ldm.minimax.model.Attention`，真实维度）：

```
qkv_proj.in_features = 5376
heads*head_dim      = 7168
自测真实构造的 x.shape = (8, 7168)
   ★ 抛异常: RuntimeError : mat1 and mat2 shapes cannot be multiplied (8x7168 and 5376x21504)

正确构造 x.shape = (8, 5376)
   max|diff| = 0.0
   allclose(1e-3) = True
```

而 `_attn_head_selfcheck` 的兜底是：

```python
except Exception:
    return False          # ← 任何异常都变成 False
```

于是 `RuntimeError` 被吞掉，`install_low_vram_attention` 拿到 `False`，
**统一报成「attn.forward 里含跨 head 操作」**。

**结论：`attn.forward` 完全没问题。用正确维度跑，整段 vs 分 8 组的结果是
逐元素完全相同（`max|diff| = 0.0`）。头分块在这台机器上是 100% 装不上的，
而且和「跨 head」毫无关系。**

### 2.3 为什么自带 checker 没抓到这个 bug

`tools/check_attn_head_chunk.py` 的桩是：

```python
class StubAttention(nn.Module):
    def __init__(self, hidden=64, heads=8, head_dim=8, eps=1e-6):
```

`8 × 8 = 64 == hidden` —— **输入维恰好等于特征维**，正好绕过这个 bug。
所以这个 checker 从写出来那天起就不可能发现它。

**对照组**：FFN 分块的自测用的是

```python
inf = int(w.shape[1])                       # upscale.py:2613，正确
x = torch.randn((rows, inf), device=w.device, dtype=w.dtype)
```

同一个文件里，FFN 那边取的是权重的 `in_features`，是对的。
所以这是**头分块这一处单独的疏漏**，不是系统性设计问题。

### 2.4 一句话

> 「选了但没开」= 探针把一个 `RuntimeError` 误判成了「架构不等价」。
> 修掉 `upscale.py:2295` 一个词，分块就能装上；同时必须把
> `except Exception: return False` 拆开，否则下次还是误诊。

## 4. 问题三：二采空间都分了 4 块，为什么还 OOM？

四条，按重要性排序。

### 4.1 OOM 的触发点根本不在空间分块管得着的地方

本次二采里出现的 OOM 有两处，**都不是 `refine_tile` 覆盖的「采样激活」**：

**(a) 权重侧 —— LoRA 应用**（15:22:16 / 15:34:13）：

```
ERROR lora diffusion_model.token_refiner.blocks.0.mlp.fc1.weight
  Allocation on device 0 would exceed allowed memory. (out of memory)
  Currently allocated : 690.65 MiB   Requested : 588.00 MiB
ERROR lora diffusion_model.token_refiner.blocks.1.attn.qkv_proj.weight
  Requested : 441.00 MiB
ERROR lora diffusion_model.token_refiner.blocks.0.mlp.fc2.weight
  Requested : 294.00 MiB
```

`lora.py` 在**把 LoRA 增量应用回权重**时要新分配一份权重（fc1 一次要 588MB）。
空间分块切的是采样中间激活，管不到这里。

**(b) 解码侧 —— 高清 VAE 解码**（15:46:05）：

```
Warning: Ran out of memory when regular VAE decoding, retrying with tiled VAE decoding.
```

这是**最终致命的那一次**。空间分块只在 UNet 采样阶段生效，VAE 解码是另一段
（由官方 `handles_tiling=True` 自己分块），`refine_tile` 完全够不着。

### 4.2 6GB 卡上根本没有余量，插件自己早就警告过

```
[H3性能] 余量策略：⚠ 显存余量策略为默认：DynamicVRAM 已启用但 `--vram-headroom` 为 0、
  也未给 `--reserve-vram`——0.35 起显存会被吃到接近 100%，二采（高清采样 + 放大网络）最先炸。
  Comfy 编译器在跑（0.35 新增，官方定位就是拉高 H3 显存利用率）。
  建议启动加 `--vram-headroom 1`；仍不稳再加 `--disable-comfy-compiler`
  （实测显存 100% → ~77%，代价约 5% 耗时）。
```

埋点实测印证：

```
refine_peak: vram_used 5.9997GB / vram_total 5.9997GB
hint: 显存已吃到临界：精化峰值 6.0GB / 总量 6.0GB，只剩 0.0GB
```

`--vram-headroom 0` + Comfy 编译器在跑 = 显存被主动吃到 100%。
**这是二采 OOM 的直接前提条件，而且它和「分几块」无关。**

### 4.3 关键线索：OOM 时 torch 只占 222MiB，但 CUDA 报 0 bytes 空闲

```
Currently allocated     : 221.99 MiB
Requested               : 112.31 MiB
Free (according to CUDA): 0 bytes
```

请求只有 **112MiB**，torch 自己才占 **222MiB**，却一点都拿不到。
说明这 6GB 不是被「激活」吃掉的，而是被**非 torch 的预留占死**：

- comfy-aimdo 的 DynamicVRAM 权重页缓存（21.1GB 模型在 6GB 卡上靠它换入换出）；
- Comfy 编译器（0.35+）的 buffer；
- 放大网络 659MB —— 插件自己写了：
  `放大网络 659MB 是裸 nn.Module：ComfyUI 的显存账看不见它、也不会按需挤占`。

而 comfy 的 `free_memory()` **只看得见自己的 ModelPatcher 账**，看不见 aimdo 原生预留。
所以日志里是：

```
15:46:04.975  0 models unloaded.
```

**没有东西可卸** —— 不是「卸了还 OOM」，是「comfy 认为压根不需要卸」，
于是 VAE 解码一分钱都借不到，regular 和 tiled 两条路都当场死。

> 这也解释了插件的警告里那句：「运行时改 `EXTRA_RESERVED_VRAM` 的第三方节点
> 只影响 Python 侧记账，盖不到 aimdo 原生预留。」

### 4.4 顺带：`refine_tile` 的 overlap 被静默夹小了，而且日志显示的是「请求值」

`perf.plan_tiles`（`perf.py:1043`）有一条硬上限：

```python
ov = min(ov, max(1, min(H // rows, W // cols) // 2))    # 上限 = 半块边长
ov = max(0, ov - (ov % 2))                              # 取偶数
```

本次 `H=44, W=76, rows=cols=2` → `min(22, 38) // 2 = 11` → `ov = 11 - 1 = 10`。
**你填的 32 实际生效 10。** 而日志打印的是请求值：

```
精化空间 tile 76×44 → 4 块（档位 2x2 · overlap 32px · 羽化 16px）
```

（同一段代码的注释里正好吐槽过这个坑：「踩过：3x3 用 16 而实际 10」——
但打印语句没跟着改成 `eff_ov`。）

## 5. 问题四：解码为什么足足 5~6 分钟？

### 5.1 最硬的一条证据：同一件事，二采里只要一半时间

| 解码 | 时刻 | 耗时 |
|---|---|---|
| 一采的基础解码（608×352，124 帧） | 14:49:24 → 14:55:50 | **386s** |
| 二采内的基础解码（**同样** 608×352，124 帧） | 14:56:55 → 14:59:57 | **183s** |

**同样的输入、同样的 VAE、同样的机器，差 2.1 倍。** 差别只有一个：

- **一采解码时，21.6GB UNET（310 个 LoRA patch）还在场。** 采样刚结束，
  权重页缓存占满显存与主机内存，而当时 `可用内存 2GB + swap 10/20GB`；
  插件也点了名：「本次卸载会把权重挤出到 swap……Windows 有 pagefile，不会 OOM kill，
  但会把采样拖到分钟级」。
- **二采解码时，UNET 还没载入**（要到 15:01:52 才为精化载入），
  显存里只有 TE + 两个 VAE，没有争抢。

> 所以「解码 388s」不是解码本身的固有成本，**是「谁在场」决定的**。
> 它是被权重换页拖慢的，不是被 VAE 拖慢的。

### 5.2 固有成本也确实不低：官方分块 + fp32 + sm75

- **官方层就已经分块解码**（`comfy/sd.py:1038` `handles_tiling=True`）：
  `tile_size=256`、`tile_overlap_min=64`、`clip_length=17`、`vae_ratio_t=4` →
  时序每块 ~20 帧。一采 608×352 约 3×2 空间块 × 7 时序块 ≈ **42 次 tile 解码**，
  386s / 42 ≈ **9s 一块**。
- **VAE 是按 fp32 载入的**：`VAE load device: cuda:0, offload device: cpu, dtype: torch.float32`。
  GTX 1660 SUPER 是 **sm75**：没有 fp32 tensor core、没有 TF32，
  而 `minimax_h3_video_vae_int8_convrot` 的 int8 只量化了 Linear，
  3D 卷积仍然是纯 CUDA core 跑 fp32。
- 二采是 1216×704 → 约 5×3 空间块 × 7 时序块 ≈ **105 次 tile 解码**（2.5 倍）。
  即使不 OOM，也要 ~1000s 量级。

### 5.3 插件为什么没有「解码分块」旋钮

`perf.py:134-138` 写得很清楚，这是**刻意移除**的：

```
⛔ VAE 解码分块（decode_chunk_on / decode_chunk_frames）已整体移除：
  H3 视频 VAE 在官方层就已 tile 级分块解码（comfy/sd.py:1038 handles_tiling=True：
  256px 空间 × 17 帧时序块，且显存估算 frames = min(frames, chunk_frames + 2) 只按单块算）。
  外面再套一层是与官方 tile 叠加 → 更慢更糊、显存一点不多省。
```

所以解码这一块**没有可调的旋钮**，只能从「别让权重占着显存」入手。

## 6. 修复建议（按性价比排序）

| # | 动作 | 位置 | 预期效果 |
|---|---|---|---|
| 1 | **修 `x` 的输入维度**：`heads * head_dim` → `attn.qkv_proj.in_features` | `upscale.py:2295` | 头分块立刻能装上（已实测：改对后自测通过、结果逐元素相同） |
| 2 | **拆开自测的兜底**：把 `except Exception: return False` 改成带原因的返回 | `upscale.py:2305` | 不再把「跑不起来」误报成「架构不等价」 |
| 3 | **启动加 `--vram-headroom 1`**（仍不稳再加 `--disable-comfy-compiler`） | ComfyUI 启动参数 | 显存从 ~100% 降到 ~77%（插件实测值），给 LoRA 应用与 VAE 解码留出余量 |
| 4 | **打开块交换**：`blocks_swap_on: true` + `blocks_to_swap: 6` | `perf.json` / 前端 | 埋点实测「放出 6 块 ≈ 多预留 **2.53GB**（块大小 0.42GB）」 |
| 5 | 二采高清解码兜底：把放大倍率从 2× 降到 1.5×，或缩短段长 | 导演台 | 1216×704 的 tile 数从 ~105 降到 ~60 |
| 6 | 让 checker 用**真实维度**的桩（`hidden ≠ heads*head_dim`） | `tools/check_attn_head_chunk.py` | 这个 bug 类别以后能被抓到 |
| 7 | 日志打印 `eff_ov` 而不是请求值 | `upscale.py:2098-2100` | 「填 32 生效 10」不再静默 |

⚠ 注意 #3/#4 二选一或叠加都行，但**别同时把 `--vram-headroom` 调大又打开块交换**，
两者都在抬 aimdo 预留，6GB 卡上会把可用权重缓存压到 2GB 以下，反而拖慢采样。
建议先只做 #3。

## 7. 还没闭环的一点（如实说明）

**精化每步 310s vs 一采每步 91s，这个 3.4 倍没能完全算平。**

能算平的部分：精化是放大后画幅（空间 4 倍），每块实际覆盖
`38+10 × 22+10 = 48×32`（相对全幅 `76×44` 约 46%）→ 每步 ≈ 91 × 4 × 0.46 ≈ **167s**。
观测 310s，**余下约 1.86 倍**，最可能来自：

1. **每个 tile 一次完整 UNET 回载** —— 日志里 4 次 `Requested to load MiniMaxH3`
   （`21603MB Staged`），即 4 × 21.6GB 权重重新装载；
2. **LoRA 应用在显存不足时退化**（§4.1a 的 588MB 分配失败）；
3. tile 之间的 `_sampler_out_to` 设备拷贝 + `edge_weights` 融合开销。

要确认得加一次对照实验（关 `refine_tile` 跑一遍精化，或临时关 LoRA），
本次运行的数据不足以进一步拆分。

**为什么不直接做成开关**（这条是本次最重要的判断）：

- `--vram-headroom` 的落点是 `main.py` 启动时交给
  `comfy_aimdo.control.init_devices` 的**每设备**预留 —— 进程一起来就定死。
  aimdo 0.5.5 公开的预留 API 只有两个：`init_devices()`（启动，每设备）与
  `set_simple_vram_headroom()`（**运行时可写**，进程级 simple budget）。
  前者**没有**运行时可写的入口 → 「面板勾一下 = `--vram-headroom 1`」做不到。
  写一个不生效的开关，比不给更糟（本项目已有 4 处 ⛔ 注释在讲这件事）。
- `--disable-comfy-compiler` 同理：决定 `comfy.model_management` 的模块级常量与
  CUDA graph 子特性，只在启动时读一次。
- **但「留出余量」这件事运行时可做**：`--reserve-vram` 除 Python 侧
  `EXTRA_RESERVED_VRAM` 外还会喂 aimdo 的 `simple_vram_headroom`，而后者有 setter
  —— 面板的「块交换 → 交换块数」接的正是它（`apply_blockswap` → `_set_aimdo_headroom`）。

所以 `launch_args_report()` 只做三件事：① 如实摆出启动参数现状；
② 给一行**可直接粘的完整命令**；③ 标出哪一项有运行时等价旋钮（`runtime_ok`）。

档位设计（决定进不进那行命令）：

| 档位 | 项 | 行为 |
|---|---|---|
| `primary` | `--vram-headroom 1`、`--use-ck-attention` | 低风险、收益明确 → **进推荐命令** |
| `fallback` | `--disable-comfy-compiler` | 有约 5% 耗时代价，口径是「仍不稳再加」→ **只提示，不进命令** |
| `alt` | `--reserve-vram` | 有运行时等价物，加了要白重启一次 → **只标注，从不推荐** |

判据与 `vram_headroom_advice` 同一口径：`--vram-headroom` / `--disable-comfy-compiler`
只在 **「DynamicVRAM 开 + 一点余量预留都没给」** 时才标缺；`--use-ck-attention`
只在用户真开了注意力头分块时才提（否则是噪音）。

同时把「块交换」的文案改成把结论放最前面 —— 它是**唯一能「不重启就留出显存余量」
的旋钮**，二采 OOM 时先来这里，不必改启动参数。这是本次「能力早就有、但用户
找不到」那类问题的直接修复。

**语义与优先级**（写死在 `apply_blockswap`，并在 UI 文案里说清）：

- 与 `blocks_to_swap` 写的是**同一个 aimdo 值**（`simple_vram_headroom`），
  只是单位不同：块数 × 块大小 = GB。**两者都填时以本项为准**，且 note 里会说明
  「「交换块数」本次未参与」—— 单一真源仍在那一个值上，不叠加、不打架。

- 夹取口径与 `blockswap_headroom` 相同：上限 = `显存 × 0.5 − 基线`，被夹如实报出。

### 11.2 ★ 订正一处此前的说法：两项预留是**独立的**，不是替代关系

`comfy_aimdo.control.set_simple_vram_headroom` 的官方 docstring（本机 0.5.5 实测读出）：

> Set the VRAM the simple budget keeps free, in bytes. **One process wide value**,
> compared against each device's own capacity. **It is separate from the per device
> extra_vram_headroom given to init_devices().** Only the simple budget term reads it;
> the measured poll term keeps its own compile time floor of **256 MB (VRAM_HEADROOM)**
> and the budget takes the **larger of the two**, so raising this above 256 MB is
> honoured but **lowering it below 256 MB changes nothing**. Raising it takes effect at
> the next VBAR fault or hooked device allocation and is honoured by **evicting VBAR
> pages only**; torch allocations are counted against it but never refused.

三条结论（都已落进代码注释与 UI 文案）：

1. **`--vram-headroom`（每设备 `extra_vram_headroom`，`init_devices` 时定）与面板
   「显存预留」（进程级 simple budget，运行时可写）是两项独立预留** ——
   **可叠加、不互相替代**。之前口头说成「等价」是不准确的。
2. **256MB 编译期地板**：填到 0.25 以下等于没填。已加常量 + note 提示。
3. 「torch allocations 被计入但**从不被拒**」→ 这个旋钮是**软目标**（逼 vbar 驱逐
   页面），不是硬保证。所以它是「把余量腾出来」，不是「锁住余量」。

本机 6GB + UNET 21.1GB 口径实测（`reserve_demo`，基线 0.59GB）：

| 填值 | 目标预留 | note |
|---|---|---|
| 0（默认） | 0.59GB | 关闭 → 已恢复进程启动时的预留 |
| 1.0 | **1.59GB** | 显存预留 +1.00GB；读回核验 |
| 1.5 | **2.09GB** | 显存预留 +1.50GB；读回核验 |
| 5.0 | **3.00GB** | 被夹到 2.41GB（显存一半 3.0 − 基线 0.59） |
| 0.1 | 0.69GB | ⚠ 低于 256MB 地板，填更小不会更省 |
| 块交换 -1 + 预留 1.0 | 1.59GB | ⚠ 已按「显存预留」计算，「交换块数」本次未参与 |

### 12.2 ★ 启动命令：粘到哪里 + 按本机适配

用户的两个问题都指向同一处设计缺陷。

**(a)「复制给哪里用」** —— 原实现输出的是**完整命令行**
（`python main.py --flags`），但用户实际是通过 **ComfyUI Desktop 顶部的
「启动参数」输入框**加参数的（截图里那一栏只有 `--enable-manager`）——
那个框**只吃 flags**，不含 `python` / `main.py`，所以粘不进去。

修法：`launch_args_report` 现在同时返回两个字段，UI 也分两块：

| 字段 | 内容 | 用在哪 |
|---|---|---|
| `args` | **仅 flags**，如 `--vram-headroom 1 --use-ck-attention` | ★ 主按钮「复制启动参数」→ 粘到 Desktop 的「启动参数」框 |
| `cmdline` | 完整命令（保留原 argv + 追加 flags） | 收进折叠层，按钮「复制完整命令」，终端启动用 |

**(b)「会根据设备实际情况调整说法吗」** —— 之前**不会**：判定只查
「DynamicVRAM 开 + 余量未给」，跟卡大小无关，于是**24GB 卡上也喊
`--vram-headroom 1`**（对没余量问题的人毫无意义，还把真紧张的卡那行盖掉）。

现在按 VRAM 分三档：

| VRAM | `--vram-headroom` | `--disable-comfy-compiler` | `--use-ck-attention` |
|---|---|---|---|
| < 12GB | **报缺**，why 写「余量紧张，强烈建议加上」 | **报缺**（余量紧张才值这 5% 代价） | 只看是否开了头分块 + kitchen 是否可用 |
| 12–24GB | 报缺，why 写「边缘卡，加 1GB 稳一手」 | 不报（why 写「余量足够，不建议加」） | 同上 |
| ≥ 24GB | **不报**，why 写「装得下时可省」 | 不报 | 同上 |
| 探不到 | 报缺（保守） | 不报 | 同上 |

实测（本机口径 `reserve_demo` 同款桩）：

```
6GB  → 缺 [--vram-headroom, --disable-comfy-compiler]   args='--vram-headroom 1'
12GB → 缺 [--vram-headroom]                             args='--vram-headroom 1'
24GB → 缺 []                                            args=''
48GB → 缺 []                                            args=''
None → 缺 [--vram-headroom]                             args='--vram-headroom 1'
```

**(c) 新增 `--use-ck-attention` 的可用性判断** —— 它是「头分块要拿 int8 kitchen
那份收益」的前提，但**没装 comfy_kitchen 时加了也没用**。所以现在探一下：
不可用就**不报缺**，why 里写明「当前环境没装 comfy_kitchen，加这个 flag 也不生效」
—— 免得用户加了 flag 重启后发现没区别，又以为是「改了没用」。

### 12.3 顺带修掉一个真 bug：说明里的字面星号

新加的 JS 断言抓到的：`launch_args` 的 `note` / `why` 文案里有 `**启动时**` 这类
markdown，但渲染时直接塞进 `innerHTML`，**星号原样露在界面上**。

根因是转换逻辑**散落在一处**：只有性能面板的字段 `hint` 那一行做了

## 13. 第四轮：新增「📖 启动命令速查」（弹窗 + txt 导出）

> 这一轮与 OOM 分析无关，是本日同批交付的**新功能**，在此只留索引。

用户要的是：顶栏在「⚡ 性能优化」旁加一个入口 → 弹窗里放 ComfyUI 启动参数说明
+ **特别详细的 Linux 部署**（开机自启 / 端口 / 防火墙 / 反向代理 / Docker / 云平台），
**每条命令一个独立复制按钮**，并**另外导出一份 txt**（不能只在 ComfyUI 里可见）。

**主交付物**：`docs/ComfyUI启动命令速查.txt`（795 行 / 17 分区 / 148 条）。

**单一真源**：`launch_ref.py` 的 `SECTIONS` —— 弹窗与 txt 都由它生成，
前端**不硬编码任何命令**（JS 断言在 `openLaunchRef` 函数体里搜 `--listen` /
`systemctl` 等字面量，出现就红）。

**两条核心守卫**（都在 `tests/test_launch_ref.py`）：

1. **不许编造 ComfyUI 参数** —— 解析 `comfy/cli_args.py` 的 `add_argument("--x")`，
   逐个核对文档里出现的每个 `--flag`（本次 72 个全过）。凭印象写参数是这类文档
   最容易犯的错，而后果是用户复制去执行直接报错。
2. **txt 不许过期** —— 磁盘那份必须与实时 `to_text()` 逐字一致；另钉 **LF 换行**
   （这份要拿到 Linux 上边看边敲，CRLF 会让命令带上 `\r`）。

### 13.1 去掉每条重复的 `python main.py`（用户反馈后修）

用户：「咋所有命令前面都有这一行，把要加的东西列出来不就得了」—— 对。
