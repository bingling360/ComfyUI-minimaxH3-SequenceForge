## 0. 已确定的口径（别推翻）

| 项 | 口径 |
|---|---|
| `--vram-headroom` | **不采用**。0.35 把显存吃到接近 100% 是官方有意拉高 H3 利用率，预留换来的是权重缓存变小、每步多重读权重 —— 有好有坏。应对放在**节点端**（按实测余量自行腾挪 + 给用户开关），不出启动参数建议 |

### 批次 1 · 显存：LoRA 探测 + 主干 OOM 自救（P0，不动画质）

**1.1 主干采样加 OOM 自救**
- 证据：日志3 两次主干 OOM，ComfyUI 自己的 `unload_all_models` 连救两次都失败。
  崩点 `hyperflow apply.py:49` 的 `F.linear(F.linear(x, down), up)`，单次请求 **6.13 GB**。
- 做法：把 `upscale.py:1844` 那一套（捕获 OOM → `unload_all_models()` + `gc.collect()`
  + `empty_cache()` → 原参重试）抽成公共函数，接到 `nodes.py:3065` 的 `ksampler_with_sigmas`。
- 验收：主干 OOM 时能自救成功或给出可行动的中文报错，不再直接抛到 ComfyUI 层。
- 进设置：`oom_autoretry`（默认 True）。

**1.2 LoRA / bypass 激活探测**
- 证据：ComfyUI 的 `model_size()` 只算**权重**（挂 HyperFlow 后 19995→32427 MB，
  这 +12.4 GB 它算到了）；算不到的是 **bypass adapter 前向的临时激活**（6.13 GB 那次）。
- 做法：`perf.probe_lora_footprint(model)` ——
  ① 从 `ModelPatcher.patches` 累加字节 → `lora_weight_gb`（与 model_size 交叉验证）；
  ② 主干第 1 步用已有的 `perf.watch_vram_peak()` 采设备级峰值，减基线 → `act_peak_gb`。
  日志打一行「LoRA 账：权重 +12.4GB（50 patches）· 实测单步激活峰值 6.1GB · 建议留空 ≥7.3GB」。
- 接线：`act_peak_gb` 反向喂给腾挪 / `blocks_to_swap` 决策。
- 进设置：`act_peak_probe`（默认 True）。

### 批次 2 · 分块（用户点名要的，按风险递增做）

| 顺序 | 项 | 画质影响 | 备注 |
|---|---|---|---|
| 2.1 | **FFN 分块** `ff_chunk_tokens` | **无（数学等价）** | 首选。OOM 正崩在 FFN（`model.py:211` 的 swiglu）。KJNodes 有同款 `MiniMax H3 Chunk FeedForward`，本机已装该节点包可参考 |
| 2.2 | attention 后端 `attn_backend`（auto/sdpa/sage/flash） | 无 | SageAttention 在 30 系有失败报告，必须留 fallback |
| 2.3 | 放大网络时序分块（**已实现**，只差暴露开关）`upscale_chunk_frames` / `upscale_overlap` | 无 | 日志已在跑 T=107→4 块，chunk 32 / overlap 5 |
| 2.4 | 精化时序分块 `refine_temporal_chunk` / `refine_temporal_overlap` | 低（接缝闪烁） | 需 overlap ≥ 8 latent token + 配合 seam_doctor |
| 2.5 | 精化空间 tile `refine_tile` / `refine_tile_overlap` | **中高（全局注意力被切断 → 色调/构图不一致）** | **默认关，UI 标「实验」** |

- 参考依据：精化耗时与帧数**严格线性 ~2.5 s/帧**（T=37→94s，T=87→192s，T=107→268/277s）；
  画布 1312×736→1728×960（+78% 像素）直接 OOM。**降帧是线性收益，降画布是防 OOM 开关，不可替代。**

### 批次 3 · 内存：成片合成（P0，收益最大）

- 证据：`nodes.py:3160 all_frames.append` + `3333 torch.cat(all_frames)` → **峰值 2×**。
  1312×736 float32 每帧 11.59 MB，8 段 ×107 帧 = 9.9 GB，cat 峰值 ≈19.8 GB，
  再叠 31.7 GB 常驻权重 → 60 GB 机器就是悬崖。
- 3.1 **逐段编码 + 流式拼接，根除全链帧 tensor**：`media.concat_av_mp4` 已经是流式的
  （帧不进 Python 累积），`upscale.try_final` 已在高清路径这么干 —— 只差把**基础分辨率**路径也接过去。
- 3.2 帧存 **uint8** 而非 float32（内存 ×¼）。
- 3.3 `torch.cat` → 预分配 + copy（3.1 的退而求其次，峰值 2×→1×）。
- 3.4 落盘守卫接行为 `guard_action`（critical 时禁止全卸）。
- 进设置：`final_mode`（auto/stream/memory）、`frames_dtype`（float32/uint8）。
- ⚠ **别指望 GPU 编码救内存**：帧最终还是要落 CPU 侧进编码器。
  实测 557 帧编码只要 13 秒 —— **编码根本不是瓶颈**。

### 批次 4 · 显存权重流动
