## 0. 先说结论：6GB 显存 / 16GB 内存能不能跑

**能跑通 ≠ 能用。** 先看三个与分辨率无关的硬数字：

| 项 | 量 | 出处 |
|---|---|---|
| UNET（int8，hybrid_fl2va_ref2va_b25-49） | ~20 GB | 实测 `model_size` 19995 MB；挂 HyperFlow LoRA 后 **32427 MB** |
| 文本编码器（int8） | **25.3 GB** | 项目已定口径：「沿用 int8，非 50 系 nvfp4 没硬件加速」 |
| 放大网络 | 0.66 GB | F16 |
| **权重合计** | **45 – 57 GB** | **与画布、帧数、分块全部无关** |

### 0.1 关键判断：分块压的是激活，不是权重

- **6GB 显存**：H3 = 50 个 double block，每块 ≈ 0.4 GB → 6GB 卡（实际可用 ~5.5GB）只放得下 **约 13 个 block**。剩下 37 个 block 每个前向都要搬 → 单次前向 **≈ 29.6 GB** 走 PCIe（进出各一次）
  - PCIe 4.0 x16 ≈ 20 GB/s → 1.5 s/前向（纯搬运）
  - PCIe 3.0 x8（大量小板/笔记本）≈ 6 GB/s → **5 s/前向**
- **16GB 内存**：放不下 45 GB → **至少 30 GB 落在 pagefile**，每次换入都可能触磁盘
- 于是：**"一采 0.2 分辨率"降的是 token 数（平方关系，这是真有效），但权重那 45 GB 一分不少。**

### 0.2 二采到 0.9 的问题

token 数按分辨率**平方**增长：0.2 → 0.9 = 4.5× 边长 → **激活 ≈ 20 倍**。分块能压，但在这个量级下：

- 块切得越细，kernel 启动开销占比越高（社区在 32GB 卡上实测 `chunk 32/16` 与 `16/8` 相差 0.8%，但那是"装得下"的前提）
- 6GB 卡是**无论如何都装不下**，粗块会落进"超显存但不 OOM"的带里全程走 PCIe 分页 —— 比多几次 kernel 启动贵得多

### 0.3 给你们的实话

| 目标 | 判断 |
|---|---|
| 一采低分辨率 + 全分块 + 大 pagefile | **可以跑通**，速度量级「每段十几分钟到一小时」，不是「勉强能用」 |
| 二采放大到 0.9 | **大概率不可行**（激活 + 权重搬运双重压力） |
| 真要在这台机器上用 | **唯一有效手段是换更小的量化权重**（GGUF Q4 级，UNET 可压到 5–8 GB）。但这与项目既定口径「不动权重精度（int8 是生态基线），fp8/GGUF 作废」正面冲突 → 需要你重新拍板 |

### 0.4 两个与分块无关、但同样致命的问题

1. **0.2 分辨率的画面内容 ≠ 0.9 应有的内容。** 扩散模型在 token 数极低时出的是「色块级」画面，二采只能补高频细节，**补不出五官、纹理、结构**。放大倍率 4.5× 也远超放大网络的训练范围（通常 1.5–2×），`max_upscale_scale` 在场景 B 的建议值就是 1.5。
2. **「0.2 / 0.9」的基准必须先定义。**
   - 若指 1920×1080 的 0.2 = 384×216、0.9 = 1728×972 → 基线勉强有讨论空间
   - 若指 1312×736 的 0.2 = 262×147 → latent 仅 33×18，patch 化后 token 极少，**基本出不了画面**
   - 这个数直接决定整个方案可行性，必须先确认。

> **强烈建议的前置动作**：先在一段 5 秒片段上做一次「零新分块 + 最大 pagefile + 最小画布」的实跑，拿真实耗时和可用性，再决定要不要把全部分块做全。
> 在一个 6GB 机器上不可用的功能做全，是最大的浪费。

## 2. 八类分块的技术方案

> 通用约定：**每一类都给「启用开关 + 参数」两件套**，关闭时参数控件禁用。
> 参数命名统一带单位后缀，避免上次那种「两个 overlap 同名不同量纲」的坑。

### A. FFN token 分块（已实现，补两个参数）

- **切法**：沿 token 行切 `fc1` / `fc2`。`nn.Linear` 沿行可分离 → **数学等价、逐位相同**，int8 激活也按 token 行量化，量化模型同样精确。
- **现状**：`ff_chunk_tokens` = 每块 token 数（0=关），装前 `_ff_chunk_selfcheck` 自测，不通过不装。
- **待补**：
  - `ff_chunk_min_tokens`（**低于此 token 数不切**）—— 对齐 KJ 的 `seq_threshold`（默认 4096）。短序列切块只增加开销。
  - 建议默认：`ff_chunk_tokens = 4096`、`ff_chunk_min_tokens = 8192`（首次开启时给一个「能省显存又不至于太碎」的值，而不是让用户从 0 猜）
- **风险**：无（自测兜底）。

### B. 注意力头分块（**新增**）

- **切法**：沿注意力 head 分组，逐组算 attention。**head 之间独立 → 精确**。
- **移植依据**：KJNodes `MiniMaxLowVRAMAttention`（`nodes/minimax_nodes.py`）。它同时做两件事释放内存：
  1. qkv GEMM 之后**立刻释放** normed hidden
  2. out_proj 分配输出**之前**释放融合的 qkv buffer
- **实现点**：patch `comfy.ldm.minimax` 的 attention `forward`。⚠ 这依赖 ComfyUI 内部结构，**必须带版本守卫 + 失败静默跳过**（对齐 `install_ff_chunking` 的「装不上就不装」策略）。
- **参数**：`attn_head_chunks`（1–8，默认 1=关）。
- **风险**：中（依赖上游内部实现，跨版本可能失效）。必须同样做**装前自测**。

### C. 块交换 blockswap（**最大工程**）

- **不是分块计算**，是把 block 权重在 GPU / CPU 之间搬。语义与 A/B 完全不同 —— 前端**不应与分块混在同一组**。
- **现状**：`perf.suggest_blocks(unet_gb, vram_gb)` 已能按显存反解块数（本机 16GB → 19–25 块），且 `H3_DOUBLE_BLOCK_COUNT = 50` 常量已就位。
- **可行路径**：项目**已经在用**块级 hook —— STG 跳过块的补丁走的是 `set_model_options_patch_replace(..., "dit", "double_block", ...)`，**这是已验证的注入点**。
- **前置条件（硬）**：
  1. **PCIe 基准实测**：「搬一块 0.4 GB 的耗时 vs 单块计算耗时」。搬 > 算 → 开了纯亏。项目文档 §5.4 已列明这是唯一硬约束。
  2. **锁页内存与 16GB 内存正面冲突**：换出的块必须在 pinned 内存（不可换页），16GB 档约 13 GB 常驻锁定 → **在这台机器上是硬账**。
  3. 显存碎片；与 STG 的 `double_block` hook 顺序必须定义。
- **参数**：`blocks_to_swap`（0–50）、`prefetch_blocks`（0–4）、`non_blocking`。
- **风险**：机制性（不改计算，但 PCIe 可能净亏）。

#### C.1 前置实测结论（2026-09-23，本机 GTX 1660 SUPER / 6GB / PCIe 3.0 x16）

脚本：`tools/bench_blockswap_pcie.py`（真 torch 独立 runner，`<ComfyUI根>/.venv` 跑，退出码 0 = 测出）。
搬的字节固定 `--block-gb 0.4`（= 20GB/50 块），取 15–20 次中位数：

| tokens × hidden | H2D | D2H | 来访成本（换入+换出） | 算一块（下界） | 搬/算 |
|---|---|---|---|---|---|
| 2048 × 1536 | 36.18 ms | 34.86 ms | 71.04 ms | 7.24 ms | **9.813** |
| 4096 × 2048 | 35.83 ms | 35.19 ms | 71.02 ms | 25.66 ms | **2.768** |
| 8192 × 2048 | 36.37 ms | 34.85 ms | 71.22 ms | 52.04 ms | **1.369** |
| 16384 × 2048 | 36.63 ms | 35.02 ms | 71.65 ms | 103.51 ms | **0.692** |

- PCIe 有效带宽实测 **~11 GB/s**（H2D 11.0 / D2H 11.4；PCIe 3.0 x16 理论 16 GB/s 打七折，正常）。
- 搬 0.4 GB 恒 **~36 ms/向**（固定成本，与 token 无关）；「算」随 token 线性增长。
- 「算」是**保守下界**（两次 hidden² GEMM，未含 attention 的 S² 项）→ 真实比值只会更小，
  但**下界已 ≥1 的档位（≤8k token）结论已足够**：搬比算还慢。

⚠ **本节结论（「不实现」）已被 §8.10 取代** —— 2026-09-23 用户拍板重开并已落地。
原因是本节的判据用错了坐标系：块交换是**换时间换显存**的生存手段，不是提速手段，
「搬/算比 ≥1」不能用来否它；且真正的机制在 ComfyUI 官方那边（见 §8.10）。

**结论（历史记录）：本机块交换纯亏 → 不实现。** 保留面板接线（`UNWIRED_KEYS` 4 项不动），
在 UI 说明里如实标注「本机实测搬/算 ≥1，开了纯亏」。仅在 token 数很大（≥16k）时比值才落进
0.5–1.0 —— 那也只是「换生存不换速度」，且本机 6GB 装不下 20GB UNET，块交换是唯一活路而非提速手段。
⚠ **换卡/换 PCIe 代次必须重跑**（如 4090 + PCIe 4.0 x16 ≈ 2× 带宽 → 比值约为本机一半，可能翻盘）。

### D. VAE 解码时序分块（**优先级最低**）

- H3 VAE **本来就内部分块**（`perf.py:96` 注释原文）。再切一层可能纯增开销。
- **前置动作**：先量一次实际解码峰值，确认是否真的有需要。**没量到问题就先不做**。

#### D.1 前置实证结论（2026-09-23）：官方已在 tile 级做完 → **不做**

源码实证（**`comfy/sd.py:1023-1057`，MiniMax H3 video VAE 分支，非注释传言**）：

- L1023 分支判定：`elif "decoder.transformer_blocks.0.scale1" in sd and ...:  # MiniMax H3 video VAE`
- L1038 `self.handles_tiling = True`；L1037 注释原文：
  `# the model tiles internally (256px spatial, 17-frame temporal chunks)`
- L1041-1042：`# one decoded temporal chunk (with overlap) is all that ever sits in VRAM`；
  `chunk_frames = (tokens_chunk_size + token_overlap) * vae_ratio_t`
- L1051-1057 `estimate_decode_memory`：`frames = min(frames, chunk_frames + 2)`
  —— **官方显存估算只按单块算，与总帧数无关**（即解码显存不随长度线性增长）。
- L1302 / L1308-1310：`handles_tiling` 为真时走
  `_decode_tiled_owned(tile_x=256 // spacial_compression_decode(), overlap=tile // 4)`。

**结论：官方已在 tile 级（256px 空间 × 17 帧时序块）完成分块解码，并配了显存估算。**
外面再套一层时序分块 = 与官方内部 tile 叠加 → 更慢更糊，**不做**（有据不做）。
本机 6GB 卡也**量不到**解码峰值（跑不动 20GB UNET），§D 的前置条件无从满足。
`upscale.py:2617-2619` 注释已在案：「它本来就内部分块解码，不存在 OOM 才降级这个动作」。

### E. 放大网络 3D 时序分块（已实现，补参数透传）

- **切法**：`[B,C,T,H,W]` 沿 T 切，每块左右多带 `overlap` 帧上下文，只取中间有效区，块间**线性 ramp 权重叠加**（`out_full / weight_full`），首块左侧、末块右侧不 ramp。
- **现状**：`upscale_net.py:377` 已实现；`_TEMPORAL_CHUNK = 32`，overlap 从 `TemporalConv3D.dwconv.weight.shape[2]` **动态读取**（实跑 5）。
- **待补**：
  - `upscale_chunk_frames` 透传到 `forward`（把模块常量改成参数，带范围校验）
  - ⚠ **overlap 不允许调小**：它等于时序卷积核宽度，小于核宽就会真的丢上下文。**只允许调大**，或干脆只读显示、不给改。
- **风险**：低（overlap 足够时与整段前向只有数值噪声级差异）。但**关掉会改变输出口径 → 必须进指纹**（现有行为，保持）。

### F. 精化时序分块（**新增，需配合接缝医生**）

- **位置**：`upscale.render_latent` 的精化采样循环。把高清 latent 的 T 切段，**逐段独立跑 N 步去噪**，段间按 latent token 重叠融合。
- **与 E 的本质区别（关键）**：
  - E 是**纯前馈**（一次 forward，无循环）→ 切开逐块算再融合即可，可控
  - F 是**扩散采样循环** → 每段独立收敛，段与段之间没有注意力交互 → 接缝两侧会收敛到不同的局部解 → **接缝逐帧闪烁**（不是静止的缝）
- **参数**：`refine_temporal_chunk`（帧数，0=关）、`refine_temporal_overlap`（**latent token**，建议 ≥ 8）。
- **前置**：`seam_doctor` 目前能处理到什么程度需要先确认（它能磨平缝，但不能恢复跨段丢失的信息）。
- **风险**：低–中（接缝闪烁）。

### G. 精化空间 tile（**新增，风险最高**）

- **位置**：同 F，切 H/W 成 2×2 / 3×3，逐块独立采样 + 像素级 overlap 融合。
- **参数**：`refine_tile`（off / 2x2 / 3x3）、`refine_tile_overlap`（**像素**，16→建议 32–64）。
- **风险分层（这是本方案里唯一有技术分歧的一项）**：
  - **2×2**：每块仍有 1/4 画幅，全局构图/光照的损失相对可控，缝只有 1 竖 1 横。**可以试。**
  - **3×3**：每块只有 1/9 画幅，全局构图基本断裂，「整体光照方向、色温统一」会明显崩，缝也难掩。
  - **视频比图像严重得多**：图像 tile 的色调不一致是静态的，肉眼可能忽略；视频里块边界会在**帧间抖动/闪烁**，因为每块独立去噪、噪声轨迹不同。
- **一处已有的内部矛盾要一并处理**：`docs/性能优化工程_改造计划_2026-09-17.md` §5.6 把 SelfLift 的 `highres_tiling` 列为「**明确不做**」，理由是「无跨块注意力 → 帧内竖缝，与 seam_doctor / 接缝精修方向相反」。
  而 `refine_tile` 的注释是「实验：**切断全局注意力**」—— **这是同一个判据**。
  按项目自己的逻辑，这一项的结论其实已经写好了。要做，就必须同步修订 §5.6 的口径（说明「为什么对它和对 SelfLift 的判断不同」），否则文档自相矛盾。
- **建议**：先只做 2×2，3×3 留到 2×2 实测有数据之后再决定；且必须带**羽化宽度**参数，不能只靠固定 overlap。

### H. 音频处理（本项目比 SelfLift 省事的一点）

SelfLift 的 `highres_tiling` 要额外处理「只保留第一个 tile 的音频」。本项目**音轨不参与精化**（音轨不重采样、沿用原声）→ **F/G 都无需处理音频**。这一点写进文档，避免后续误加。

## 3. 前端阶段化排布方案

### 3.1 分类轴：从「按资源类型」改成「按处理链阶段」

现状是 `显存 / 内存 / 编码 / 运行时开关 / 素材库`（按**资源类型**），这正是「同一件事散在两个组里、找不着」的根源。改成按**阶段**：

```
① 一采采样（主干扩散）      二级：分块 · 注意力 · 权重流动
② VAE 解码                  二级：分块
③ 放大网络                  二级：分块 · 常驻
④ 精化二采                  二级：分块 · 腾挪 · 守卫
⑤ 成片与编码                二级：合成 · 编码
⑥ 通用与机器                二级：自救 · 运行时 · 素材库
```

**规则**：
- 每条分块归到它**实际生效的那一段**（用户脑子里想的也是「我现在卡在哪一段」）
- 跨阶段的资源策略（`vram_shuffle` 腾挪、`guard_action` 守卫、`oom_autoretry` 自救）归 ⑥ 或就近的阶段，但**必须在一级标题上写清「跨阶段」**
- 一级标题右侧带 **生效时机徽章**：`立即生效` / `下次渲染`
- 一级标题显示 **可调项数**（现有代码已在做，保留）

### 3.2 控件形态统一：「启用开关 + 参数」两件套

现状是三种形态混用：`0=关` 的数值（`ff_chunk_tokens`）、bool 勾选（`upscale_temporal_chunk`）、下拉即开关（`refine_tile`）。用户看不出「这个分块到底开没开」。

**统一方案**：给字段加 `enable` 属性，指向前置开关 key：

```js
{ key: "ff_chunk_tokens", enable: "ff_chunk_on", ... }
```

- 渲染时 `enable` 的 checkbox 控制参数的 `disabled`
- **后端只需一个数**：`enable=false` 时写 `0` / `off`，不引入第二个存储键
- 关闭态参数显示为灰 + 保留用户上次填的数（别清零，重开还在）

### 3.3 每个阶段一个「一键」按钮（你要的「各阶段开启按钮」）

在每个一级标题右侧加：

## 4. 右栏「重叠项」的真实关系 —— **两处你说错了**

我把右栏 `renderUpscaleZone` 与性能弹窗逐项比对了：

| 右栏项 | 弹窗对应项 | **真实关系** | 处理建议 |
|---|---|---|---|
| 基础二采 →「时序分块」`up.chunk` | `upscale_temporal_chunk` | ✅ **同一个东西**（bool × bool） | **删右栏**，保留弹窗 |
| 基础二采 →「强制卸载」`up.force_unload` | `keep_upscaler_resident` | ✅ **同一个东西的取反面**（`resident = !force_unload`） | **删右栏**，保留弹窗 |
| 基础二采 →「编码档位」`up.encode`（标准/高清/极致） | `encoder` + `nvenc_cq` | ❌ **不是一回事** | **不能简单删**，见下 |

### 4.1 编码那一处必须先说清：项目里有**三个**编码设置，维度各不相同

| 位置 | 名字 | 管什么 | 取值 |
|---|---|---|---|
| 节点控件（`nodes.py:992`） | 「一采编码」 | 基础链分段的编码质量档 | 标准 / 高清 / 极致 |
| 右栏二采 | `up.encode`「编码档位」 | 二采分段 + 高清成片的质量档 | 标准 / 高清 / 极致 |
| 性能弹窗 | `encoder` + `nvenc_cq` | **用哪个编码器实现** + 质量数值 | libx264 / h264_nvenc / hevc_nvenc + cq |

- `up.encode` 落在 `upscale.ENCODE_PROFILES`，是 **(crf, preset, 抖动, dither)** 四元组（`upscale.py:42-51`，如「极致」= crf13 + slow + 抖动）
- `media.set_encoder` 是**选实现**（x264 vs NVENC）+ cq

**两者可以且应该组合**（例：高清档 + NVENC）。**删掉 `up.encode` 会丢掉「crf / preset / 抗条纹抖动」整个能力**，只留「用哪个编码器」。

→ **建议：不删，而是「合并到弹窗的编码区」**，两个控件并排，并在说明里点明二者正交。这样「所有编码设置在一处」，且不丢功能。

### 4.2 删除后的指纹连带影响（**必看**）

`upscale._hash_params` 里这两行是**条件化**的：

```python
if cfg.get("chunk") is False:        keys["chunk"] = False      # 关掉才进指纹
if cfg.get("force_unload"):          keys["force_unload"] = True # 开了才进指纹
```

**删掉右栏控件、把这些判定一并删除** → 所有「当年显式关过分块/开过强制卸载」的既有段，指纹会变 → **被判失效、重做**。

**处理办法**（三选一，见 §7 待决策）：
- **甲**：保留从 manifest 读取的路径，只是不再暴露 UI（老项目仍按存档值跑，新项目不写这个值）。代价：全局设置与项目存档可能打架，需在面板上显示「本项目存档覆盖中」。
- **乙**：把分块整体改成**机器级全局设置，不进指纹**。理由：分块是**显存手段不是画质手段**，本来就该跟着机器走。代价：同一项目里新旧段可能用了不同分块口径（但 A/B 类数学等价，影响极小）。
- **丙**：保持现状不删，只在弹窗里把它们标成「项目级」并加上跳转。

## 5. 作用域设计（这是整个方案的地基）

必须先把一件事钉死：**分块是机器级还是项目级？**

| | 机器级（`perf.json`，跨项目共用） | 项目级（`manifest`，进二采指纹） |
|---|---|---|
| 适合 | 显存/内存手段：分块、块交换、编码器、自救 | 输出口径：放大倍率、STG、锐化、编码质量档 |
| 改动的后果 | 影响后续所有段 | 既有段被判失效 → 重做 |

**建议口径**：
- **A/B/C/D/E/F/G 全部分块 → 机器级，不进指纹**（它们的目的就是「同一台机器上跑得动」，与作品无关）
- **但 `upscale_temporal_chunk` 例外**：关掉会真实改变输出 → 保留进指纹的现有行为，并在 UI 上明确标「此项改变输出口径」
- 放大倍率、STG、锐化、`encode` 档 → 继续留在项目级

   自测的 reference 路径再调 `attn(…)` 会进那个普通函数（self 位置收错）→
   自测必然失败 → 第二次调用误报「含跨 head 操作」，连已装的都判为不该装。
3. **★ 实例属性赋普通函数 ≠ 绑定方法** —— `attn.forward = _fwd` 是给**实例**挂属性，

   ```
   m.forward = plain          # TypeError: plain() missing 1 required positional argument: 'x'

   ```

   `def _fwd(x, ..., __n=eff, __sa=attn)`（既补回 attn，又避免循环里闭包晚绑定）。
   ⚠ 这与 `install_ff_chunking` 的 `_fwd(x, *a, ...)` 是**同一个坑**，那边早就踩过。

### 8.10.1 查证结论：块级权重流动**官方早就做了**，不是本项目缺功能

| 证据 | 位置 |
|---|---|
| H3 block 循环里已有预取/换入队列 | `comfy/ldm/minimax/model.py:751-765`：`make_prefetch_queue(list(self.blocks), …)` + 每块 `prefetch_queue_pop(…, block, malloc_scope="block")` |
| 总闸 | `comfy/model_base.py:250`：`transformer_options["prefetch_dynamic_vbars"] = self.current_patcher.is_dynamic()` |
| `is_dynamic()` 真 ⟺ 动态 patcher | `comfy/model_patcher.py:1795`；`main.py:300` 在 aimdo 可用时 `CoreModelPatcher = ModelPatcherDynamic`（`sd.py` 的 `load_diffusion_model_state_dict` 用的就是它） |
| 机制链 | `prefetch_queue_pop → pin_modules → ops.cast_modules_with_vbar → comfy_aimdo.model_vbar.vbar_fault`（锁页主机内存 ↔ vbar）+ 异步 offload 流 |
| op 时基线换入 | `comfy/ops.py:167` → **关预取 ≠ 关块级流动**，只去掉 lookahead |
| 本机实测 | `.venv` 跑 `comfy_aimdo.control.init()→True`、`init_devices→True`、`NUM_STREAMS=2`、pinned 6.34GB、预留基线 **0.25GB** |

⚠ 两个探针坑（都踩过）：
1. **必须先 `ctl.init()` 再 `init_devices()`** —— 不先 init 时 `lib is None`，`init_devices`
   直接 return False，会误判成「aimdo 不可用」。
2. `comfy.memory_management.aimdo_enabled` 与 `CoreModelPatcher = ModelPatcherDynamic`
   **只有 main.py 会设**（`main.py:300-301`）→ 独立进程里要手工复刻这两步才能得到真实判定。

### 8.10.2 为什么**不自己写**手工块交换（三条硬理由）

1. **一个算法只能有一个来源**（项目铁律）：手工 swap = 第二个主人，与官方 `partially_load` /
   vbar 抢同一批参数。
2. **打坏 LoRA**：HyperFlow 走 comfy 的 patch 链，权重搬走再回来与 `model_loaded_weight_memory`
   的账、`_prefetch` / `lowvram_function` 缓存全脱节。
3. **aimdo 下根本搬不动**：权重住在 vbar（`m._v`），官方明禁外部 pin ——
   `ModelPatcherDynamic.pin_weight_to_device` → `RuntimeError("...invalid for dymamic weight loading")`。
   老版本（无 aimdo）也不是空白：`ModelPatcher.load()/partially_load()/_load_list()` 就是按
   **模块**流（粒度 ≈ block）。→ **两种模式权重归属都是 ComfyUI 的。**

| `blocks_swap_on` | 保留 | 总开关；关 → **恢复 baseline**（不是保持上次设的值） |
| `blocks_to_swap` | 保留（-1 跟随档位） | N 块 → 目标预留 = N×(UNET/50) → `comfy_aimdo.control.set_simple_vram_headroom()`（真调 + **读回核验**）。语义与面板 1:1；**超过显存一半会夹取**并在报告里说明 |
| `prefetch_blocks` → `blocks_prefetch` | **改 bool** | 官方预取深度由 `prefetch_queue_pop` 的队列结构写死为「提前 1 块」→ 只能开关（`upscale.install_block_prefetch` 包 DiT 的 `_forward`） |
| `non_blocking` | **删** | 官方恒 `non_blocking=True`，且锁页内存是 aimdo 的硬前提（关不掉、也放不掉）→ 留着就是假开关 |

无 aimdo 的环境不退化为「没救」：`blocks_to_swap` 折成 Python 侧 `EXTRA_RESERVED_VRAM`
（`load_models_gpu` 的「最低必须留空」地板），同样改变「留多少在卡上」。

落点：`perf.py`（`probe_blockswap` / `blockswap_headroom`〔纯函数〕/ `_blockswap_baseline`
〔只读一次并缓存〕/ `_set_aimdo_headroom` / `_set_extra_reserved` / `apply_blockswap` /
`blockswap_line`）、`upscale.install_block_prefetch`、`nodes.py`（渲染开始 `apply_blockswap` +
模型侧预取开关）、`web/h3_director.js`（字段三项 + 诊断区新增「块级权重流动现状」一行 + 保存回执）。

### 8.10.4 ★ 两条必须守住的纪律

1. **读接口不许改进程状态**：`perf_get` 也会走 `apply_runtime → apply_blockswap`，而面板打开时
   拿不到 UNET 体量。此时若按「extra=0」照写，会把**渲染时设好的预留悄悄抹掉**。→ 算不出目标
   就 `return`，一次 `_set_*` 都不许调（两个分支都加了守卫，单测钉住）。
2. **基线只读一次并缓存**：第二次读到的可能已被我们自己改过 —— 不缓存会让「关掉开关 = 恢复
   原样」变成「关掉开关 = 保持我上次设的值」。

### 8.10.5 顺手修掉一处**既有缩进 bug**（HEAD 里就有，与本批无关）

二采报告块（`_tb` …）与其 `elif _up_err:` 被挂在 `if _ff_tokens > 0:` / `if _ah_n > 1:` 之下 →
**关着分块时报告里整段二采参数消失**、二采跳过原因挂到无关条件上。根因是历史上「在它前面插入
if 块」的改动把守卫（原为 `if up_cfg:`）与函数体拆开了。修法：在 `_tb` 前补一行 `if up_cfg:`，
并用 AST 核验（`elif _up_err` 现挂在 `if up_cfg` 下）。
