## 0. 一句话结论

**瓶颈不是「用了多少显存」，而是「26 GB 的 UNET 挪不动」。**

- 场景 A（32GB 卡）：占 83%，**刚好装得下** → 优化重点在**别让它落盘**
- 场景 B（16GB 卡）：占 163%，**装不下** → 优化重点在**让它有序地流动**

**权重精度不动**（int8 是生态基线，LoRA 与注意力机制均为此适配）**是全局硬约束。**

## 1. 目标形态

### 1.1 硬件与运行配置

**你最终打算的形态：**

```
一采模型 ── LoRA 组① ──[ModelAttentionBackend = comfy kitchen attention]──┐
                                                                          ├─→ H3SeamlessChainSampler
二采模型 ── LoRA 组② ──[块稀疏注意力 sol-attn]──────────────────────────────┘
```

- **二采模型本身与一采相同，只是 LoRA 不同**（← 这条改变了很多结论，见 §5.3）
- 注意力走 `comfy kitchen attention` 后端
- 训练侧挂 `sol-attn` 块稀疏注意力：`tau=1.30` / `start_percent=0.20` /
  `end_percent=1.00` / `min_tokens=12288` / `extra_tokens=256` /
  `sink_condition=exact_kv_and_rows`

### 1.2 这套注意力栈意味着什么（对性能工程的影响）

| 事实 | 影响 |
|---|---|
| `ModelAttentionBackend` 已在默认工作流里（`web/h3_default_workflow.js`、`example_workflows/备用初始化导演台工作流.json`） | 「换 attention 后端」从**建议**变成**已就位** → 面板只做确认与诊断 |
| 块稀疏注意力**在注意力层压激活值**，不碰权重精度 | **完全兼容 int8 约束** ✅ 是本工程的一等公民 |
| `min_tokens=12288` | **只有 token 数超阈值才生效** → 小画布 / 短段它不起作用；大画布 / 长段才是它的战场 |
| `start_percent=0.20` | 前 20% 采样仍走 dense |
| 它压低了激活峰值（R_a） | **剩下的瓶颈更集中在 26 GB 权重** → **块交换的相对收益变大** |

⚠ **块稀疏的参数本身就是显存 / 速度旋钮**（`min_tokens` 越低越省、`tau` 越大越省），
应当收进性能面板做**只读镜像 + 生效提示**，而不是另造平行开关。

## 2. 两种部署场景与判据

### 2.1 场景定义

| | **场景 A · 云端（你自己常用）** | **场景 B · 本地（使用者最常见）** |
|---|---|---|
| 系统 | Linux | Windows |
| 显存 | **32 GB** | **16 GB** |
| 内存 | **60 – 90 GB** | **32 GB** |
| 磁盘 | **几乎没有** | **大量** |
| 特征 | 高显存 + 大内存 + **无落地空间** | 小显存 + 小内存 + **有大落地空间** |

### 2.2 三条判据

| 判据 | 公式 | 它决定什么 |
|---|---|---|
| **R_v** | UNET 权重 ÷ 可用显存 | 模型能不能**常驻** |
| **R_m** | (UNET + TE) ÷ 可用内存 | 卸载是落**内存**，还是被 OS 换出到 **swap / pagefile** |
| **R_d** | 可用磁盘（含 swap）÷ 重量级 | 能不能承受"落盘"这件事 |

实测：

| | R_v | R_m | R_d |
|---|---|---|---|
| **场景 A** | 26/31.36 = **0.83**（常规档） | 51.9/60–90 = **0.58–0.87**（**<1 → 落内存**） | **紧张 → 绝不能落盘** |
| **场景 B** | 26/16 = **1.63**（极限档） | 51.9/32 = **1.62**（**>1 → 必然落盘**） | 充裕 → 落盘可接受 |

### 2.3 ⚠ 场景 A 的隐藏风险：Linux 无 swap 会直接被杀，不是变慢

这一点必须单独说，因为它是**静默致命**的：

- 场景 A 内存 60–90GB，看似够装 51.9GB 权重
- 但**落点由 ComfyUI / 操作系统决定，插件不控制**。若内存被其它进程占用，
  权重会被换出到 **swap**
- **云端机器常常没配 swap，或 swap 极小，而且磁盘本来就快满**
- → 结果**不是"变慢"，而是进程被 OOM killer 直接杀掉**（或把磁盘写爆）

**→ 场景 A 必须新增一条护栏**：
启动时算 `可用内存 + 可用 swap` vs `权重总和 × 1.2`。
不足时**明确报**「本次卸载会落盘，而本机 swap 仅 X GB / 磁盘仅 Y GB ——
建议先释放内存，或接受被 OOM 杀掉的风险」，而不是让它静默发生。

## 3. 场景 A 方案（云端 Linux · 32GB 显存 · 60–90GB 内存 · 无磁盘）

### 3.1 特征与策略取向

**R_v = 0.83 → 权重装得下；R_m < 1 → 卸载落内存。这其实是最舒服的场景。**

策略取向：**守住「权重要么在显存、要么在内存，绝不落盘」**。
优化重点是**速度**，不是省显存。

### 3.2 方案

| 项 | 设定 | 理由 |
|---|---|---|
| 块交换 | **关（0 块）** | 权重装得下，开了纯亏 PCIe |
| 段间卸 UNET | **否** | 卸了要重新回载 26GB，白白多一趟 |
| 解码前卸 UNET | 跟随 `_up_swap` | 同 base 只差 LoRA 时本来就不卸 |
| 解码分块 | **关** | 显存够，分块只增加开销 |
| 放大倍率上限 | **4.0**（不限） | 32GB 撑得住 |
| cond 缓存容量 | 32（现状） | 内存充裕 |
| 放大网络常驻 | **保留缓存**（`force_unload` 关） | 内存够，段间零加载 |
| **落盘守卫** | **开（新增）** | 见 §3.3 |
| 二采调度 | 跟随生成 | 同 base 只差 LoRA → 无交替换页（§5.3） |

### 3.3 场景 A 唯一需要新做的东西：落盘守卫

```
启动时：
  need = UNET + TE 权重总和 × 1.2        # 51.9 × 1.2 ≈ 62 GB
  have = 可用内存 + 可用 swap
  if have < need:
      报告 ⚠ 严重：本次卸载会把权重挤出到 swap
      并显示：可用内存 X GB / 可用 swap Y GB / 可用磁盘 Z GB
      若 Y 或 Z 也不足 → 建议先关掉其它进程，或降级为不卸载策略
```

这条**只读、不改行为**，但能避免"跑了两小时被 OOM 杀掉"。
建议放在阶段 1（与面板同时落地）。

## 4. 场景 B 方案（本地 Windows · 16GB 显存 · 32GB 内存 · 大磁盘）

### 4.1 特征与策略取向

**R_v = 1.63 → 权重装不下；R_m = 1.62 → 卸载必落盘（好在磁盘够）。**

策略取向：**让 26 GB 有序地流动 + 把激活值压到最小**。
优化重点是**能跑起来且不至于慢到不可用**。

### 4.2 方案

| 项 | 设定 | 理由 |
|---|---|---|
| **块交换** | **`blocks_to_swap` ≈ 25**（50 块的一半） | 16GB 卡的主力手段；有顺序、有预取，可被计算掩盖 |
| `prefetch_blocks` | 2 | 掩盖搬运 |
| `non_blocking` | 开 | 更快，但多吃内存（本场景内存紧，需权衡） |
| 段间卸 UNET | **是** | 反正装不下 |
| 解码分块 | **32 帧** | 削解码峰值（P2-2） |
| 放大倍率上限 | **1.5×** | 激活值随倍率平方涨 |
| cond 缓存容量 | **8** | 省内存 |
| 放大网络常驻 | **`force_unload` 开** | 省 659 MB 内存，段间重新加载 |
| 帧落 CPU | 开 | 削解码后峰值 |
| **磁盘余量守卫** | 开 | 避免系统盘写满；确认 pagefile 所在盘有空间 |
| 二采调度 | 跟随生成（§5.3） | 同 base 只差 LoRA，无交替换页可省 |

### 4.3 场景 B 的顺序（按收益）

1. **让块稀疏注意力真正生效** —— 检查画布/段长是否达到 `min_tokens=12288`。
   达不到 → 它一点没帮上忙，此时**降画布/缩短段**比任何调度手段都直接。
2. **块交换** —— 唯一能撼动 26 GB 权重的杠杆。
3. **降低放大倍率 / 段长** —— 直接线性/平方地降激活。
4. **内存项**（`force_unload`、cond 缓存容量）—— 顺手就能开。

## 5. 综合手段清单

### 5.1 【已就位】注意力栈

- `comfy kitchen attention` 后端 + `sol-attn` 块稀疏 —— **不碰权重精度，兼容 int8** ✅
- 面板职责：**只读镜像 + 生效提示**
  （例：`块稀疏：min_tokens=12288，当前画布 token≈8.4k → 未生效`）。
  这条提示比任何"预算"都有用 —— 它直接告诉你**优化有没有在起作用**。

### 5.2 【场景 B 主力】块交换 + 预取

- 生态出处：`ComfyUI-WanVideoWrapper` `WanVideoBlockSwap`（kijai）、LongCat FP8 工作流。
- H3 = **50 个 double block**；每个 ≈ 0.52 GB。
- 参数换算（原表 14B/40 块 → H3/50 块）：16GB → **19–25 块**；12GB → 31–38；8GB → 44–50。
- **为什么比 aimdo 分页好**：有顺序、有预取。WanVideo 实测每块
  `load=0.023s / compute=0.145s` → **搬运小于计算，预取可完全掩盖**。
- 本项目已有基础设施：STG 跳块**已经在用** `set_model_options_patch_replace(..., "dit", "double_block", ...)`，
  `H3_DOUBLE_BLOCK_COUNT = 50` 常量已在 → **块级 hook 是已验证路径**。
- **代价见 §5.4。**

### 5.3 ⚠【重要修正】同 base 只差 LoRA —— 两遍式在你这里没有省头

这是 v3 最关键的一条修正。

你的配置是「**二采模型与一采相同，只是 LoRA 不同**」。而代码里：

- `upscale.models_distinct()` 专门判掉了「同一份权重只差 LoRA」（共享 `clone_base_uuid`）
- `nodes.py:1672` 注释：「同 base 的克隆（只差 LoRA）**不卸**——卸了等于把二采自己搬走，纯浪费」
- → **`_up_swap = False` → 不触发 UNET 级换页**

**结论：v1/v2 里「每段 2 次换页、2N 次」那笔账，在你的配置下不存在。**
→ **两遍式（先跑完全部一采、再跑全部二采）对你没有省头。**
（此前两轮我先后说过「2N→2」和「2N→1」，都以「A≠B 是两份独立权重」为前提；这个前提不成立。）

⚠ **但这是代码的判断，不是实测**：LoRA 补丁的重新应用是否导致权重重传，
取决于 ComfyUI 的 patch 机制。**建议先实测**：看每段二采里 `MiniMaxH3`（UNET）
被回载了几次。

⚠ **2026-09-22 真机实测后的判据修正（原判据会假阳性）**：
一次 `render_segment` 内部**必然**会打 3 条 `Requested to load`——
TE（建高清 cond）、UNET（精化前 `unload_all_models()` 之后的回载）、VAE（解码）。
这三条都是代码主动触发的既定流程，**与「换 LoRA 是否重传」无关**。
故判据不能是「有没有出现」，必须是 **UNET 被回载 ≥2 次**
（第 1 次是既定的，第 2 次才是重传）。现由 `perf.classify_loads()` 分类统计。

| 实测结果（UNET 回载次数） | 含义 | 动作 |
|---|---|---|
| **0 次** | 确认零换页 | 两遍式**不必开**，去掉这条建议 |
| **1 次** | 只有既定那次回载 | **证据不足**，「两遍式」仍需单独实测，别下结论 |
| **≥2 次** | 确实在重传 | 两遍式**重新有价值**，按「2N → 1」算 |

真机那次读到的是 **A≠B=False、总回载 3 次（UNET 1 次）→ 证据不足**，
旧代码却直接打印了「同 base 换 LoRA 确实在重传」，属假阳性。

### 5.4 块交换的代价（逐条算清）

1. **PCIe 带宽 —— 唯一硬约束**
   - 每前向搬 `25 × 0.52 × 2`（进+出）≈ **26 GB**；若前向 5 秒 → 需 **5.2 GB/s**
   - PCIe 4.0 x16 ≈ 20 GB/s → 余量约 4 倍，**近乎免费**
   - ⚠ **PCIe 3.0 x8 ≈ 6 GB/s** → 余量仅 1.2 倍，会拖后腿（**不少 16GB 卡是 x8**）
   - → **动手前必须先测本机 PCIe 与单块计算耗时**
2. **锁页内存 —— 与场景 B 的内存瓶颈正面冲突**
   - 换出的块必须在 pinned 内存（不可换页、不可回收）→ 16GB 档约 **13 GB 常驻锁定**
   - ⚠ 在 32GB 内存机器上是硬账 → **必须与 §5.5 内存优化捆绑推进**
3. **显存碎片**；**与 aimdo 叠加语义未知**（须实测两种组合）；
   **与 STG 跳块补丁的 `double_block` hook 顺序必须定义**

### 5.5 内存（RAM）—— 两场景都相关，取向相反

| 项 | 场景 A | 场景 B |
|---|---|---|
| 主要矛盾 | **别落盘**（无 swap → 会被 OOM kill） | **落盘太频繁**（每次 26GB 走 NVMe） |
| 放大网络 CPU 副本 659 MB | 保留 | **`force_unload` 开** |
| cond 缓存 32 条 | 保留 | **降到 8** |
| `up_v_base` CPU fp32 副本（mix>0） | 保留 | 改 bf16 |
| ComfyUI 节点输出缓存（本节点自述输出「完整视频+音频」） | 大内存能扛 | **建议 `--cache-lru 1`** |
| 高清解码帧（P2-2 未做） | 无所谓 | **落 CPU** |

**多段变卡**（已上报症状）的候选成因与确认方法见 v2 §2.8，顺序不变：
① ComfyUI 节点输出缓存 ② 放大网络 CPU 副本 ③ `up_v_base` ④ cond 缓存 ⑤ 解码帧 ⑥ 模型缓存双份。
**先加每段 RSS 埋点定位，不要猜着改。**

### 5.6 【明确不做】的

| 手段 | 为什么不做 |
|---|---|
| 降精度 / 量化 | **用户已否决**（int8 是生态基线） |
| 上下文窗口 / 滑窗 | **本项目已用段链实现**，不引入第二套 |
| TeaCache 式跳步 | 与二采「细节增益」冲突 |
| T8 的「工作区上限 MiB」 | **反例**：实测真实占用仅 **7.90 MiB**，调低只增加分块数 |
| SelfLift 的 `highres_tiling` | 无跨块注意力 → **帧内竖缝**，与 seam_doctor / 接缝精修方向相反 |

## 6. 性能设置面板设计（右栏第 5 分区）

### 6.1 位置

右栏现有 4 分区：`rParams` · `rExp` · `rUpscale` · `rHist`。
**新增第 5 个 `rPerf`**，插在 `rUpscale` 之后、`rHist` 之前，标题 `⚙ 性能优化`。

### 6.2 契约 `ds.perf`

```
ds.perf = {
  // 场景
  profile: "auto",           // auto | 云端高显存 | 本地小显存 | 自定义
  preset:  "auto",           // auto | 省显存优先 | 平衡 | 速度优先

  // 显存：权重流动
  blocks_to_swap:  -1,       // -1 跟随 profile；0..50
  prefetch_blocks:  2,
  non_blocking:    true,

  // 显存：常驻
  unload_unet_seg:      "auto",
  unload_before_decode: "auto",

  // 显存：峰值
  decode_chunk_frames: 0,
  frames_to_cpu:      "auto",
  max_upscale_scale:  0,     // 0 = 不限

  // 内存
  unload_upscaler_cache: "auto",
  cond_cache_size:       "auto",

  // 磁盘 / swap 守卫（场景 A 必备）
  guard_offload_target: true,    // 落盘守卫开关
  offload_guard_ratio:  1.2,     // 需要 内存+swap ≥ 权重 × 此系数

  // 诊断
  probe: false,                  // 显存 + RSS 埋点
}
```

### 6.3 面板结构（自上而下）

1. **硬件概览行**（只读）
   `显存 32.0 GB · 内存 80 GB · swap 0 GB · R_v 0.83 · R_m 0.65 · 建议档：云端高显存`
2. **场景预设两个按钮**：`云端高显存` / `本地小显存`（一键写一组参数）
3. **注意力栈状态行**（只读，§5.1）
   `kitchen attention 已启用 · 块稀疏 min_tokens=12288，当前 token≈8.4k → 未生效`
4. **落盘守卫行**（§3.3，仅当 profile=云端时突出显示）
   `可用内存 62 GB + swap 0 GB vs 需求 62 GB → ✓ / ⚠`
5. **`<details>` 高级区**：按显存 / 内存 / 磁盘 / 诊断四组折叠
6. **诊断区**：显示每段的显存峰值 + RSS 曲线

### 6.4 必须遵守的既有铁律

- **一块 UI 一个渲染主人**：面板自己渲染，宿主 `refresh()` 只做兜底，
  本地改动走本地重建（参照 `repaintUpscale`）
- **副本签名守卫**：`perfSig(data)` 与 `upscaleSig` 同构；**`!!data.node` 必须进签名**
- **参数单一真源**：不在前端重算后端口径。面板**只显示判据、不产生判据**
- 新增 `tests/test_perf_wiring.py` 结构守卫（仿 `test_anchor_wiring.py`）

## 8. 红线段

1. **别去掉 `net.cpu()`** —— 它还是"放大前腾挪"的触发开关（09-15 已否决过改）。
2. **别去掉 `_up_swap` 的条件判断** —— 同 base 只差 LoRA 时做腾挪是纯浪费。
3. **别把 `_UNET_SIZE_CACHE` 的 id 缓存顺手重构** —— 有注释说是历史包袱。
4. **别动权重精度** —— int8 是生态基线。
5. **别动注意力栈** —— kitchen attention / sol-attn 是已采用的优化，面板只做只读镜像。
6. **新增项一律默认关 / 默认 auto，不进任何指纹**。
7. **块交换不得破坏 STG 跳块补丁**（两者都 hook `double_block`，必须定义叠加顺序）。
8. **每阶段必须能证明"成片结果不变"** —— 只允许变快、变省，不允许变样。
