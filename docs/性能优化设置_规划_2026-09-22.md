## 1. 日志实测：一次「段渲染」的六点时间线

插件每段打六个显存/RSS 采样点。三份日志里同规格（1312×736、T=107、60 GB 内存）
的两轮完整跑，逐点对照：

| 采样点 | 显存·无LoRA | 显存·挂LoRA | 内存RSS·无LoRA | 内存RSS·挂LoRA |
|---|---|---|---|---|
| 放大前 | 9.69 | 7.28 | 6.43 | 8.38 |
| 放大后 | 11.29 | 8.84 | 6.43 | 8.38 |
| cond 后 | 22.01 | 22.32 | 32.66 | 34.71 |
| 卸载后 | 9.22 | 6.84 | 6.54 | 8.58 |
| 精化后 | **23.19** | **23.18** | 26.19 | **40.38** |
| 解码后 | 21.91 | 21.87 | 32.34 | **46.54** |

（单位 GB。无LoRA = 运行日志..txt 第 3 轮；挂LoRA = 运行日志2..txt 第 1 轮）

**两条显存线几乎重合，并且在精化后都顶到 23.2/23.6 GB，只剩 0.1–0.3 GB。**
**两条内存线在「卸载后」之后分道扬镳：26→32 GB vs 40→46.5 GB。**

这一张表就是整份规划的基点，下面五条诊断全部由它推出。

## 2. 五条诊断

### D1 · LoRA 把模型体积顶大 62%，直接把「档位」翻转了

日志原文的 ComfyUI 自报体积：

```
无 LoRA：Model MiniMaxH3 prepared ... 19995MB Staged. 0 patches attached.
挂 LoRA：Model MiniMaxH3 prepared ... 32427MB Staged. 50 patches attached.
```

差 12.4 GB。后果在 `[H3性能]` 行里是连锁的：

| | 无 LoRA | 挂 LoRA |
|---|---|---|
| 模型体积 | 19.5 GB | 31.7 GB |
| R_v（模型÷显存） | 0.85 | **1.37** |
| 自动档位 | 云端高显存 | **本地小显存** |
| 可给权重缓存 | 22.4 GB | 22.4 GB |
| 每步需重读 | 0.0 GB（0%） | **9.3 GB（29%）** |

也就是说挂上 LoRA 之后，机器在 ComfyUI 眼里**从「装得下」变成了「装不下」**。

> 附带一条实测：同为 T=107、1312×736，无 LoRA 是 20 步 35.65 s/it，
> 挂 LoRA 是 8 步 36.55 s/it —— **单步耗时几乎没变（+2.5%）**。
> 说明 aimdo 的流式装载把 9.3 GB 的重读掩盖得很好。
> **LoRA 的代价不在速度，在内存和显存余量。**

### D2 · 官方探不到的不是「LoRA 权重」，是「bypass LoRA 的前向激活」

用户的判断对了一半：LoRA 的**权重** ComfyUI 其实算到了（就是上面那个
32427 vs 19995 的差，patches 进了 `model_size()`）。真正没进账的是
**bypass 型 adapter 前向时产生的临时张量**——它算激活，不算权重。

运行日志3..txt 里两次主干采样 OOM，崩点极其干净：

```
File ".../comfy/ldm/minimax/model.py", line 211, in forward
    return comfy.ops.linear_input_act(self.fc2, self.fc1(x), "swiglu")
File ".../comfy/weight_adapter/bypass.py", line 170, in _bypass_forward
File ".../ComfyUI-Hyperflow/hyperflow_h3/apply.py", line 49, in bypass_forward
    return base_out.add_(F.linear(F.linear(x, down), up), alpha=scale)
torch.OutOfMemoryError:
    Currently allocated     : 13.48 GiB
    Requested               : 6.13 GiB
    Device limit            : 23.52 GiB
    Free (according to CUDA): 23.69 MiB
```

三个事实：

1. 崩在 **FFN 的 fc1/fc2**（`swiglu`），LoRA 以 bypass 形式挂在这里。
2. **单次分配 6.13 GB**，占 24 GB 卡的 26%。`F.linear(x, down)` → rank 256 中间张量，
   `F.linear(…, up)` → 满 hidden 维输出。这是激活，不是权重。
3. `Free (according to CUDA) = 23.69 MiB`，但 torch 说只分配了 13.48 GiB——
   **中间 ~10 GB 被 torch 之外的人占着**（aimdo 权重池）。这正是既有口径说的
   「显存不能靠 `torch.cuda.memory_allocated()` 量」。

而且这两次 OOM 是**连着重试两次都炸**：ComfyUI 自己的
`[ERROR] Got an OOM, unloading all loaded models.` 救不回来，
因为救的是「权重」，不是「LoRA 激活」。

前后对照更能说明是**状态相关**的：同一份配置，日志3 第 2 轮 8 步成功
（12.27 s/it），第 3/4 轮第一步就炸，第 5 轮又成功（45.89 s/it）。

### D3 · 内存的真凶不是编码器，是「全链帧 tensor + torch.cat 翻倍」

`nodes.py` 里：

```python
2650:  all_frames = []
3160:  all_frames.append(_cf)        # _cf = frames.cpu()  → [N,H,W,3] float32
3333:  images = torch.cat(all_frames, dim=0)   # ← 峰值在这里翻倍
3354:  final_name, enc_err = _autosave_final(root, images, all_wav, ...)
```

算一下量级（1312×736，float32，每帧 11.59 MB）：

| 段数 | 帧数 | 帧张量 | `torch.cat` 峰值 |
|---|---|---|---|
| 1 段 | 107 | 1.24 GB | 2.5 GB |
| 4 段 | 428 | 4.96 GB | 9.9 GB |
| **8 段** | **856** | **9.9 GB** | **≈19.8 GB** |

`torch.cat` 会新开一整块连续缓冲，而 `all_frames` 里的分片还全被引用着，
所以峰值是 **2×**。再叠加 D1 的 31.7 GB 常驻权重 → **60 GB 机器上就是悬崖**。
日志2 实测单段解码后 RSS 已经 46.54 GB。

**而 `save_av_mp4` 本身其实很干净**：它按 32 帧分块搬运，峰值约 160 MB。
日志3 实测 557 帧编码只花 **13 秒**。**编码根本不是瓶颈。**

### D4 · swap = 0 的 Linux，没有缓冲垫

`[H3性能]` 三份日志每轮都打同一条 critical：

```
落盘守卫：⚠ 本次卸载会把权重挤出到 swap —— 可用内存 31GB + swap 0/0GB
          < 需求 81GB（权重 67.5GB × 1.2）；可用磁盘 60GB。
          本机 swap 不足，Linux 无 swap 时不是变慢而是被 OOM killer 杀掉
```

Windows 有 pagefile，挤出去只是变慢；**Linux 无 swap 是 SIGKILL，进程直接没了**。
60 GB 机器跑到 46.5 GB（78%）就已经在悬崖边——因为权重是**瞬发**需求，
不是渐进的：一次 `unload_all_models()` 就要几十 GB。

### D5 · 二采精化耗时与帧数严格线性，帧数是唯一杠杆

同模型、同画布、同 4 步、同 σ：

| 帧数 | 精化耗时 | 单帧 |
|---|---|---|
| T=37（1312×736） | 94 s | 2.54 s |
| T=107（1312×736） | 277 s | 2.59 s |
| T=107（1312×736，挂LoRA） | 268 s | 2.51 s |
| T=87（1312×736，挂LoRA） | 192 s | 2.21 s |

**2.5 s/帧，几乎完美线性。** 而画布从 1312×736 提到 1728×960（+78% 像素）
就直接 OOM（运行日志..txt 第 2 轮，"可回收显存 0.563979GB"）。

结论：**降帧数是线性收益，降画布是防 OOM 的开关**，两者不能互相替代。

## 3. 方案

### A 组 · 显存

| # | 措施 | 证据 | 代价 / 风险 | 优先级 |
|---|---|---|---|---|
| A1 | **主干采样加 OOM 自救**（把二采那套搬过来） | 日志3 两次主干 OOM，ComfyUI 自救救不回 | 几乎为零；`upscale.py:1844` 已有同机制，抽公共函数 | **P0** |
| A2 | **LoRA 激活实测 + 反向约束** | D2 的 6.13 GB | 需要一次前向采样；量到之后可自动降级 | **P0** |
| A3-1 | **Chunk FeedForward**（FFN 分块） | OOM 正崩在 FFN | **数学等价，零画质损失**；KJNodes 有同款 | **P0** |
| A3-2 | **attention 后端可切**（sdpa / sage / flash） | 本机跑的是 `nodes_sparse_attention` | Sage 在 30 系可能失败，需 fallback | P1 |
| A3-3 | **放大网络时序分块**（已有，仅暴露开关） | 日志已在跑 T=107→4 块 | 无 | P1 |
| A3-4 | **精化时序分块** | D5 线性 | 时间注意力跨块 → 接缝闪烁，需 overlap + seam_doctor | P1 |
| A3-5 | **精化空间分块（tile）** | 1728×960 OOM | 全局注意力被切断 → 色调/构图不一致；**默认关，标实验** | P2 |
| A4 | **blockswap** | `perf.suggest_blocks` 已算好：本机 n≈18 | PCIe 带宽是硬约束，需先测「搬一块 vs 算一块」 | P1 |
| A5 | **余量策略：节点端适配，不动启动参数** | `[H3性能]` 每轮都在报「`--vram-headroom` 为 0」 | 0.35 起显存被吃到接近 100% 是**官方有意为之**（拉高 H3 利用率），加 `--vram-headroom` 会把权重缓存挤小、每步多重读权重 —— **有好有坏，不给出启动参数建议**。本插件的应对是节点端：精化前按实测余量自行腾挪（已有）+ 性能设置里给出「腾挪强度」开关让用户按自己的卡选 | P1 |
| A6 | **放大网络别每段搬上搬下** | 日志里每段一条「为把放大网络 659MB 搬上卡，全卸腾挪耗时 X s」：6.3 / 8.0 / 6.4 / 5.7 / 6.7 / 3.7 s | 8 段 ≈ 40–60 s 纯腾挪；可改成常驻或整链只搬一次 | P1 |

### B 组 · 内存（成片合成）

| # | 措施 | 证据 | 代价 / 风险 | 优先级 |
|---|---|---|---|---|
| B1 | **逐段编码 + 流式拼接，根除全链帧 tensor** | D3；`media.concat_av_mp4` 已经是流式的（帧不进 Python 累积），`upscale.try_final` 已经在高清路径上这么干 | 需把基础分辨率路径也接过去；段 mp4 已在盘 | **P0** |
| B2 | **帧存 uint8 而非 float32** | D3 | 内存 ×¼；需改下游测量代码的读取 | P1 |
| B3 | **`torch.cat` → 预分配 + copy** | D3 | 峰值 2× → 1×；B1 的退而求其次 | P1 |
| B4 | **落盘守卫接行为**（critical 时禁止全卸） | D4 | 需 A/B：24 GB 卡上不卸载可能净亏 | P1 |
| B5 | **swap 运维建议**（给云端机器加 8–16 GB swap） | D4 | 运维侧，写成提示 | P1 |

### C 组 · 编码 GPU 化（诚实评估）

| 措施 | 可行性 | 真实收益 | 结论 |
|---|---|---|---|
| NVENC / NVDEC（`h264_nvenc`） | ✅ 零新依赖，PyAV 直接 `add_stream("h264_nvenc")` | CPU 占用大降；**耗时收益有限**（实测 557 帧 13 s，x264 已很快） | 做开关，低优先级 |
| GPU 上做 RGB→uint8/NV12 再回传 | ✅ 纯 torch 算子 | 回传量降 8×；但帧仍要落 CPU 进编码器，**不省 RAM 峰值** | 配合 B2 做 |
| 零拷贝 GPU→编码器（`hwupload` + filter graph） | ⚠️ PyAV 有 `av.filter.Graph`，但依赖 FFmpeg 构建带 cuda filter | 理论最优 | 调试成本高，P2 |
| 完整 NLE 式时间线 GPU 合成 | ❌ | 项目没有时间线数据结构 | 不做 |

**诚实结论：编码不是瓶颈，内存才是。** C 组整体优先级最低。

### 主流剪辑软件怎么做的（用户直接问的）

| NLE 的做法 | 技术 | 本项目能用吗 |
|---|---|---|
| 代理流 / 优化媒体 | 低分辨率副本编辑，最终渲染回源 | 部分适用（已有分段 mp4） |
| 磁盘帧缓存 | 渲染结果落盘，回放不重算 | ✅ **已有雏形**（`try_final` + `concat_av_mp4`） |
| 智能渲染 / Use Previews | 未改动片段直接复用，不重编码 | ✅ 等价 B1 |
| GPU 解码/编码 | NVDEC / NVENC / QuickSync / VideoToolbox | ✅ 可做（C1） |
| 帧留在 GPU 显存，零拷贝 | `hwupload`、CUDA filter、GPU 纹理 | ⚠️ 见 C 组 |
| 内部用 YUV 10-bit 而非 RGB float32 | 每像素 1.5–2 字节 vs 12 字节 | ✅ 等价 B2 |
| 只保留当前 GOP 参考帧 | 解码器只需要有限参考帧 | ✅ 等价 B1（逐段流式） |

最关键的一条：**NLE 从不把整条时间线的全分辨率 RGB 帧同时放在内存里。**
我们现在做了，这就是问题本身。

## 5. 落地顺序

1. **第 1 批（不动画质，纯降风险）**：A1 主干 OOM 自救 + A2 激活探测 + A6 启动建议提示
2. **第 2 批（最大内存收益）**：B1 逐段流式成片 + B2 uint8 帧 + B5 swap 提示
3. **第 3 批（面板）**：把 `perf.DEFAULT_PERF` 全部暴露成「性能优化设置」栏，补 4.3/4.4/4.5 新字段
4. **第 4 批（分块，按风险递增）**：A3-1 FFN 分块 → A3-4 精化时序分块 → A3-5 精化空间分块（实验）
5. **第 5 批（锦上添花）**：C1 NVENC 开关、A4 blockswap 实测

**待 A/B 的未决项**（不要凭 24 GB 卡的数据改默认行为）：
`upscale.py:1657` 精化前的 `unload_all_models()` 在 24 GB 卡上疑似净亏，
但 32 GB 卡上有过 OOM 实测才加的它。换卡前只做 A/B，不改默认。
判定依据已就位（`watch_vram_peak` 的精化峰值 + 日志里的「腾挪回收显存 ±XGB」）。
