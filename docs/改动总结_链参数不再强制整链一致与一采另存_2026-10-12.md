来源：用户反馈两件事 ——
① 「改个分辨率还要切项目」（旧版把画幅/时长/指纹写进自动项目目录名，且
`checkpoint.assert_match` 对分辨率不一致直接抛错，逼人「改回存档分辨率或换个新目录开新链」）；

本文同时记录**发布后审查发现的问题与修复**（§四），它们是同一批语义的收口，
后续改动请以本文的口径为准。

## 二、核心语义（跨分辨率下的行为表）

链参数不再强制整链一致后，「中途改分辨率」不再是错误，而是一种受支持的编辑：

| 情形 | 行为 |
|---|---|
| 自动项目目录 | 固定 `h3chain`，与参数**无关**；改分辨率/时长不换项目 |
| 存档段 | 保留各自**当时**的分辨率，逐段记在 `manifest.seg_res[g]` |
| 本次新生成段 | 用**当前画布** |
| 相邻段分辨率不同 · 桥取自上一段尾帧 | 跳过自动引用上段尾帧，**且本段整体按「无桥」采样**（不预留 ctx 帧、不裁头）——见 §四 ② |
| 相邻段分辨率不同 · 桥取自库/段/视频/图片（外源锚） | **照常注入**：外源由 `_resolve_anchor_latent` 先裁后编归一形状，不受分辨率约束 |
| 相邻段分辨率不同 · 接缝帧差 / 五维评测 | 跳过（跨分辨率比帧没有意义，形状不同也拼不上） |
| 全链分辨率不一致 | 本次不自动成片，只提示（改用素材库「合并导出」自行拼片） |
| 回放段 | 解盘上那份 latent：桥帧是**存档当年烘进去的**，裁头口径沿用存档值 |

判定「某一槽位是什么分辨率」的**唯一真源**是 `manifest.seg_res`；`manifest.params`
每次运行都被当前画布覆盖，只代表「上次运行用的画布」，不能当作某一段的分辨率。
后端对应 `_archived_res` / `_slot_res`，前端对应 `archivedRes(mf, g)`。

## 四、审查发现并修复的问题

发布版（`014a0fb`）本身可用，但审查出两条真 bug 与若干一致性问题，已修：

**① `_res_list()` 用当前画布兜底，会把没走到的槽位的 `seg_res` 冲掉（真 bug）**
`_seg_res_map` 只装本次循环真正走过的槽位，而 `done` 是存档里的整链完成数，两者不等
（审片/重摇中段 break 时 `done` 仍是 10、循环只走到第 3 段）。用当前画布兜底会把
未访问槽位写成「新分辨率」，而它们盘上其实是旧分辨率 → 下次运行判「相邻段同分辨率」
→ 真去拼 latent 桥 → C/H/W 不一致崩掉，正是本次改动要根除的失败。
改为逐槽问 `_slot_res`（未访问但可回放 → 存档值）。

**② 跨分辨率跳过尾帧桥时，接收段仍按 ctx 预留并裁头（真 bug）**
`skip_f = _seg_extra = int(_eff_fr) if _has_src else 0` 只看段自身属性，不看 `guide`
实际是否为 `None`。于是没有桥却照旧生成 `length+ctx` 帧、再裁掉头部 ctx 帧
（默认 22 帧≈0.9s，最大 56 帧≈2.3s）——裁掉的是**本段真实内容的前 ctx 帧**，画面整体前移。
修：`_bridge_off_res` 判据下按「无桥」采样（`skip_f=0`、`seg_len=length`），
并跳过桥帧门控。**回放段不适用**（存档 latent 里已烘进桥帧，跟着置 0 会把桥帧当内容输出）。
两处：段间交棒与序章 → 段 1。

> ①② 的判据都从 `nodes.py` 的巨型闭包里提成了纯函数（`checkpoint.ResolutionLedger`
> 与 `anchors.bridge_from_prev_tail` / `bridge_extra_frames`），并配了真行为用例——
> 发布版的测试全是源码字符串断言（`assert "xxx" in src`），只能证明"注释还在"，
> 这正是 ① 能漏到发布版的原因。

**②附：跨分辨率跳过桥接的判据收窄为「桥取自上一段尾帧」**
外源锚（库/段/视频/图片）由 `resolve_anchor_source` 先裁后编归一形状，跨分辨率照样接得上；
发布版只看分辨率差就跳过，等于把一条本来能用的显式锚废掉。现在交棒端、接收端、
桥帧门控三处都问 `bridge_from_prev_tail`。

**③ `truncate` 漏掉新键与另存件**：键表补 `base_videos` / `seg_res`；
段文件清理正则补 `(?:base_)?` 前缀（旧版 `re.match` 从头部锚定，`base_seg_NNN.mp4`
根本匹配不到，截断后残件留着）。

**④ 用户可见文案仍是旧口径**：存档目录 tooltip 与画布日志行还写「空=按参数指纹自动命名」；
`checkpoint.py` 模块 docstring 的 v4 段「真·唯一硬约束只有分辨率」与 v6 自相矛盾。

**⑤ `_adopt_legacy_auto_project` 的「最近更新」判据**：目录 mtime 只在增删文件时变，
改 manifest/段文件都不变 → 可能选错旧项目。改为优先读 `manifest.updated_at`，读不到才回落目录 mtime。

**⑥ 桥帧门控与交棒判据不同源**：`_next_wants_bridge` 取 `exec_items[item_i+1]`（不跳禁用段），
而交棒走 `_next_consumer`（跳禁用段）→ 紧邻段被禁用时两者指向不同段。改为同走 `_next_consumer`；
门控同时补上「桥必须取自本段尾帧」与分辨率两个前提（否则会为一座不存在的桥牺牲本段帧数）。

**⑦ `H3Api.perfSet` 双包**：`perfSet` 自己已包 `{perf:…}`，调用处再传 `{perf:{}}` 会发成
`{perf:{perf:{}}}`；结果因后端丢弃未知键而碰巧正确。已改为传空对象（两处）。

**⑧ `upRecValid` 与后端 `base_hash` 越界口径不一致**：后端越界用空串占位，前端旧实现
`undefined` 就判有效。已逐字对齐后端口径。

**⑨ 前端的「已存档段分辨率」用了 `manifest.params` 顶替**：`params` 每次运行都被当前画布
覆盖，只代表「上次运行画布」，混分辨率链里指不了某一具体段（重摇过靠后段时提示会指错段）。
新增 `archivedRes(mf, g)`（按槽位读 `seg_res`、`g >= done` 返回 null，与后端 `_archived_res`
同口径），页脚 / 续拍确认 / 重摇弹窗三处提示全部改走它；重摇弹窗只比紧邻的上/下段，
且已标重摇的邻居不算（它本次会按当前画布重做）。

**复核后不成立的一条**：曾怀疑「序章槽 `base_videos[0]` 恒为空」与序章会被二采矛盾 ——
实际 `_up_hi` 对 `kind != "prompt"` 直接返回 `(False, False)`，序章**从不做二采**，
注释正确，无需改。
