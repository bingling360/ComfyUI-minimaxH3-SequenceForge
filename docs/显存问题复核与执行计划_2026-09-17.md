## 2. 逐条证据

### P0-1 + P0-2：移植遗漏（最高优先级）

**铁证**——项目自己的上游快照 `docs/upstream_snapshot/2026-09-02/`：

```python

```
```python
# 上游 minimax_h3_latent_upscaler_3d.py:584（2D 版在 2d.py:451 用 no_grad）
with torch.inference_mode():
    s_norm = (s - norm_mean) / norm_std
    out = model(s_norm, scale=..., target_size=(t, h_out, w_out), enable_chunking=...)
    out = out * norm_std + norm_mean
```

本地：
```python
# upscale_net.py:880 —— 少了 .requires_grad_(False)
model = model.to(device).eval()
```
```python
# upscale.py:698-708 —— 没有任何 no_grad / inference_mode 包裹
x = video_t.detach().to(net_dev, torch.float32)
xn = (x.to(nd) - mean) / std
y = net(xn, scale=..., target_size=...)      # ← 裸调用
```

**为什么能确定是"漏"而不是"故意"**：`docs/UPSTREAM.md` §4 是一份自称完整的
「与上游的差异台账」（D1–D10），里面**没有这一条**。D5 只解释了"归一化外移到
`upscale.py`"，没解释为什么把 `inference_mode` 一起丢了。

**后果链**（已核实，见 §3）：
1. 插件全仓无 `no_grad`/`inference_mode`（只有 `metrics.py:163`、`optimizer.py:481`）；
2. 插件全仓无 `requires_grad` 设置 → 网络权重保持默认 `True`；
3. 于是前向**必然建 autograd 图**，保存全部中间激活；
4. 图被扣押跨越**整个精化采样阶段**（见 §3 的存活窗口）。

### P1-2：真实存在，但原报告的表述要修正

**原表述**（审计报告 P1-2）："高清 VAE 解码前不卸 UNET → 必然走 tiled 降级（能出但慢）"。

**修正**：H3 视频 VAE 声明了 `handles_tiling = True`（`comfy/sd.py:1020`），

所以不存在"降级到 tiled"这个动作——**它一直就是 tiled**。

**真实代价**（三条，都可核实）：
1. ComfyUI 要先 `load_models_gpu([vae_patcher], memory_required=memory_used)`
   （`sd.py:1241`）——UNET 驻留时这一步要腾挪/换页；
2. `batch_number = int(self.patcher.get_free_memory(device) / memory_used)`
   （`sd.py:1242-1244`）——可用小则退化成 1；
3. **★ 0.36 新增的 tile 批次优化被抵消**：`comfy/ldm/minimax/vae.py:590-591`
   ```python
   free = comfy.model_management.get_free_memory(z_row.device)
   batch = int(max(1, min(4, free // (128 * 2**20 * z_row.shape[0]))))
   ```
   用的是**同一个低估口径** → DynamicVRAM 下 `batch` 恒为 1 →
   b2e31e89 那个"每批多块 tile 提速 ~7%"（`vae.py:589` 注释）拿不到。

→ 所以这条的收益是**"解码更快"**，不是"避免降级"。

## 3. 两个必须知道的新事实（我前两轮漏了，已核实）

### 3.1 autograd 图的存活窗口 = 放大前向 → 精化采样结束

```python
# upscale.py:1387 建图
up_v = upscale_video(...)
# upscale.py:1497 没有 detach 就交给采样器
latent["samples"] = comfy.nested_tensor.NestedTensor(
    (up_v.to(_edev, torch.float32), audio_t.to(_edev, torch.float32)))
del up_v
# upscale.py:1732 图到这里才释放
del cond, latent
```

同设备同 dtype 时 `.to()` 直接返回原张量，所以 `latent` 一直持着带 `grad_fn` 的张量。
**→ 放大网络的整套激活被扣押跨越整个精化采样阶段**，与 UNET + 精化激活正面相撞。

**规模（实测）**：放大权重文件
`D:\Comfy-Desktop\ComfyUI-Shared\models\latent_upscale_models\minimax_h3_latent_upscaler_3d_fp16.safetensors`
= **345,280,216 参数 / 全 F16 / 659 MB**，`conv_in.weight = [512, 24, 3, 3, 3]`
（3D、channels=512、12+12 个 ResBlock）。

- 权重 **659 MB**（6GB 卡的 **11%**）——`upscale.py:765` `_cuda_if_room` 的
  docstring 写的"仅 ~0.7GB"是**对的**；
  但 `nodes.py:1243` 注释写的"约 200-300MB"**已过时**，别信那个数。
- 激活（按 512 通道 × 高清 latent 64×64 × T 帧、fp16）：每张满尺寸特征图
  T=4 时 ≈16.8 MB；autograd 下每 ResBlock 留 2 张 → 整套粗估 **0.8–1.2 GB**（T=4）。
  **这是推算，不是实测**——阶段 0 的埋点就是为了把它变成实测。
- `_TEMPORAL_CHUNK = 32`（`upscale_net.py:32`）是对 latent T 分块，
  而实际 latent T 只有 2–12 → **分块从不触发**，等于整段单次前向。

### 3.2 二采模型可能不同 → P1-2 的代价随配置变化（**重要修正**）

主节点有独立入口 `二采模型`（`nodes.py:865`，可选 `io.Model.Input`）——
它是**精化二采专用的 UNET**，与放大网络 `net` 是**两个独立入口**，别混。
`_up_model = 模型 if 二采模型 is None else 二采模型`（`nodes.py:1669`）。

好消息：**账目口径本来就是对的**——`_up_model` 传进 `render_segment`/`render_latent`
的 `模型` 形参（`nodes.py:2377`），所以 preflight / `_unet_size_gb` / `_reclaimable_gb`
用的都是二采模型；`_reclaimable_gb` 还用 `id(mp) == target` 正确排除了它自己。

**但 P1-2 修法的代价随 A/B 是否相同而完全不同**（我前两轮说错了）：

| 配置 | 精化后驻留 | 下段一采要的 | 解码前卸掉它 |
|---|---|---|---|
| **A ≠ B**（接了二采模型） | B | A（另一个模型） | **B 反正要被换出去让位 → 零额外代价** |
| **A == B**（未接） | A=B | 同一个 A=B | 要多一次回载 |

→ **接了独立二采模型时，P1-2 是零代价纯赚**；这正是用户的配置。

代码已处理 A≠B 的碎片/账目问题：`_up_swap = upscale.models_distinct(...)`
（`nodes.py:1673`）→ 为真时二采入口先 `unload_all_models()`
（`nodes.py:2353-2372`）。`models_distinct`（`upscale.py:959-979`）还判掉了
"同一份权重只差 LoRA"（共享 `clone_base_uuid`）的情况。

## 4. 综合看这个项目

### 强项（改之前先尊重这些）

- **防御式设计很扎实**：全链路 try/except + 三级 OOM 降级 + 不静默降级
  （`UpscaleAbortError` 语义明确：宁可整链停，不产出"一段高清一段基础"的混合产物）。
- **有上游跟踪机制**：`docs/UPSTREAM.md` + `docs/upstream_snapshot/` 的差异台账
  （D1–D10）——**改 `upscale_net.py` 前必读**，它明确警告
  "把本地的刻意增强当 bug 修回去"。
- **腾挪点的顺序是对的**：`unload → gc.collect() → empty_cache`，反序收不回。
- **已有 21 个测试文件**，但**只有 `tests/test_upscale_model_tag.py` 碰 upscale**，
  且只测纯函数 `model_tag`。**VRAM / 预检 / 前向路径零测试覆盖** ← 这是计划要补的。

### 三条"别动"红线（改之前先看，都是被否决过的方向）

1. **别去掉 `net.cpu()`**（`upscale.py:1460`）——它表面只腾 659MB，
   实际还是 `upscale.py:1327 if dev.type == 'cpu'` 那个"放大前腾挪"的**触发开关**。
   去掉它 → 腾挪永不触发 → 首段峰值问题常态化到每一段。09-15 已否决过。
2. **别去掉 `_up_swap` 的条件判断**——A==B 时做那个腾挪是纯浪费（卸了立刻装回）。
3. **别把 `_UNET_SIZE_CACHE` 的 id 缓存"顺手重构"**——`upscale.py:906-910`
   有明确注释说它是"历史包袱"，`model_tag` 刻意不做 id 缓存就是因为它。

### 仍开着的小问题（本轮新发现）

- **二采失败路径没卸模型**：`nodes.py:2396-2402` 只做
  `soft_empty_cache() + gc + empty_cache()`，**没有 `unload_all_models()`**。
  A≠B 时 B 可能滞留，紧接着下段一采要载 A → 两个 UNET 同时在场
  （靠 ComfyUI `load_models_gpu` 兜底，不会错，但多一次换页/碎片）。
  09-15 记为 P4。**→ 2026-09-17 已修**（按 `_up_swap` 条件加 `unload_all_models()`；
  A==B 时 B 就是 A，滞留正是想要的，卸了反而白付一次回载）。
- **0.36 的 VAE 优化有两条在本机不生效**（供参考，不是要改的东西）：
  `fp16_conv3d`/`fp16_linear` 需 `torch.backends.cuda.matmul.allow_fp16_accumulation=True`
  （**实测默认 False**）；INT8 融合需量化模型。融合的 `group_norm_silu_pad3d` 不受影响。

## 5. 执行计划

**总原则**：先量后改；一次只动一类；每阶段可独立回滚；
**P0-1/P0-2 不改变任何生成结果**（只是不再记账），是最安全的起点。

### 阶段 0：先加埋点（必做，否则改完无法证明收益）

- **改哪**：`upscale.py` `render_latent` / `render_segment` 插桩。
- **加什么**：在 6 个节点打 `torch.cuda.reset_peak_memory_stats()` +
  `torch.cuda.max_memory_allocated()`，节点为：
  放大前 / 放大后 / cond 构建后 / unload 后 / 精化后 / 解码后。
  输出到 `[H3二采] 段N 显存峰值：放大X.XXGB 精化X.XXGB 解码X.XXGB`。
- **为什么先做**：本机 `nvidia-smi` 挂了，没有别的实测手段；
  而且 §3.1 的"0.8–1.2GB"是推算，必须变成实测才能定优先级。
- **验证**：跑一段二采，日志里能看到 6 个数字且 `max_memory_allocated` 单调合理。
- **回滚**：纯日志，删掉即可。

### 阶段 1：P0-1 + P0-2（收益最大、风险最低）

- **改哪 1**：`upscale_net.py:880`
  ```python
  model = model.to(device).eval().requires_grad_(False)
  ```
- **改哪 2**：`upscale.py` `upscale_video`——用 `torch.no_grad()` 包住
  **从归一化到反归一化**的整段（`:698-708`）：
  ```python
  with torch.no_grad():
      x = video_t.detach().to(net_dev, torch.float32)
      ...
      y = net(xn, ...)
      return y.to(torch.float32) * std32 + mean32
  ```
- **用 `no_grad` 而不是 `inference_mode`**（重要）：`inference_mode` 产生
  "inference tensor"，之后在 inference_mode 之外做**原地操作会报错**
  （`Inplace update to inference tensor outside InferenceMode is not allowed`），
  而 `up_v` 要一路交给采样器，风险不可控。`no_grad` 同样阻止建图，且无此限制。
- **覆盖范围**：`upscale_video` 有 **5 个调用点**
  （`upscale.py:1387/1433/1439/1444` + `latent_tools.py:487`）——改在函数内部即可全覆盖。
- **验证**：
  1. `py_compile` + 跑 `tests/`；
  2. 跑同一段二采，**成片应逐像素一致**（可用 `pixel_sharpness` 与
     `latent_hf_energy` 的日志值比对，或直接比对输出 mp4 的帧哈希）；
  3. 阶段 0 的埋点应显示"放大后"峰值下降。
- **风险**：极低。唯一要确认的是没有下游代码依赖 `up_v` 带梯度（它不带，因为
