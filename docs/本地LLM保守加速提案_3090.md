## 原始提案（保留备查）所有结论按 3090（Ampere，24GB GDDR6X，~936GB/s 带宽）计算，
> 不是本机（本机 ComfyUI 自带 torch 是 CPU 版，仅用于开发调试）。
> 涉及文件：`optimizer.py` 的 `_local_generate()`（GGUF 路 866-900 行、Transformers 路 903-933 行）。

## 一、先定位三笔开销（按成本从大到小）

本地通道目前是"**每次调用：加载 → 生成 → 关闭句柄归还显存**"（`_local_generate` docstring 明确写了不做进程内缓存）。

| # | 开销 | 3090 上量级 | 说明 |
|---|------|------------|------|
| 1 | **权重溢出到 CPU** | 速度掉一个数量级 | 见第二节，这是"能不能跑"，不是"快不快" |
| 2 | **每次重新加载** | 冷 2–8s / 热 1–3s | 19GB 权重从 NVMe → HBM + ggml 建图，连续多次优化会累积 |
| 3 | **每次重新 prefill** | 0.5–1.5s | 系统提示 + 规则文件每次原样重算 |
| — | decode 本身 | 27B Q4 ≈ 20–28 tok/s | 带宽受限，`936GB/s ÷ 19GB` 理论 49 tok/s，实算打 4–6 折 |

**结论**：能改变体感的只有两件事——**别让层溢出**、**用小模型替大模型**（第 2、3 笔是零头级别）。
decode 的 tok/s 由硬件带宽锁死，任何"算得快"的技巧都骗不过 19GB 的搬运量。

## 二、P0｜显存保底（最高优先，几乎零风险）

3090 24GB 现状算账（`_local_generate` 当前行为）：

- 权重 Q4_K_M：27B 级 ≈ 19GB
- 视觉塔 mmproj：≈ 1GB
- **KV 缓存**：当前 `n_ctx = (max(8192, budget+8192)+511)//512*512`，
  默认 `max_tokens=8192` → **n_ctx 已经自动开到 16384**；用户改到 16384 就变 24576。
  32B 级配置（64 层 / 8 KV head / head_dim 128）fp16 KV ≈ **256KB/token**：
  16384 → 4.2GB，24576 → **6.3GB**。
- 合计 24.2G ~ 26.3G → **超过 24GB**。

`n_gpu_layers=-1` 时 llama.cpp 不会报错，只是默默把放不下的层丢给 CPU。
一旦丢层，decode 从 ~25 tok/s 掉到个位数，且**日志里看不出来**。

**P0 三条改动：**

1. **KV 缓存量化**：`type_k=GGML_TYPE_Q8_0` / `type_v=GGML_TYPE_Q8_0` → KV 显存直接减半
   （16384: 4.2G→2.1G；24576: 6.3G→3.1G）。质量损失肉眼不可辨。
2. **n_ctx 按真实需求收紧**：`prompt_tokens + max_tokens + 512` 余量，上限钉在 16384；
   不要用 `budget + 8192` 这个拍脑袋常量。省下的就是"留给权重的预算"。
3. **开跑前先让 ComfyUI 腾一圈**（这一步就是"用 ComfyUI 现成环境"）：

```python
import comfy.model_management as mm          # 全部 getattr + try/except 兜底
mm.soft_empty_cache()                        # 先把这边不用的扩散模型卸了
free = mm.get_free_memory(mm.get_torch_device())
# free 不足<｜hy_place▁holder▁no▁813｜>权重+KV+1.5G 时，降级：不加载 mmproj / 减小 n_ctx / 报错提示用户
```

**验收**：日志打印 `n_gpu_layers` 实际生效层数 与 `llama_print_timings` 的 load time。
最简单的一眼判据——**看到 "offloaded X/Y layers to GPU" 时 X 必须等于 Y**。

## 三、P1｜句柄常驻 + 让位（唯一有改造量的项）

现在"用完即卸"的初衷是对的（27B 常驻会吃掉 H3 采样的显存）。但可以用**借 nut** 的方式两全：

- 模块级缓存 key = `(model_path, mmproj, n_ctx, n_gpu_layers, type_k/v)`，命中就复用句柄；
- **让位钩子**：包一层 `comfy.model_management.load_models_gpu`，ComfyUI 每次要加载扩散模型前，
  先 drop 我们的 LLM 句柄 → 等价于现在的用完即卸，但只在该让的时候让。

```python
_orig = mm.load_models_gpu
def _patched(models, *a, **kw):
    _drop_llm_if_resident()          # 仅释放 llama.cpp 句柄 + gc
    return _orig(models, *a, **kw)
mm.load_models_gpu = _patched
```

**进阶可选**：给 `mm.current_loaded_models` 塞一个实现 `model_memory / model_unload / model_load / model_memory_required`
的轻量对象，让 LLM 完全参与 ComfyUI 的显存调度（自动被挤掉、自动参与 OOM 判定）。
缺点：`current_loaded_models` 是 ComfyUI **内部**结构，跨版本会变，必须 `hasattr` 逐个探测、失败就退回 P1 基础版。

**风险**：模型生命周期变长，dtor 时机不再是"每次调用后"，异常路径要兜住（现有 `finally: llm.close()` 要换成"标记为未使用"而非立即关）。
**收益**：连续 N 次优化只加载一次，省掉第二笔开销。

## 四、P2｜llama.cpp 原生参数（全部是已装库的现成参数，零新依赖）

| 参数 | 现值 | 建议 | 收益 / 风险 |
|------|------|------|------------|
| `flash_attn` | 未设 | `True` | 长上下文显存显著下降；**前提是 CUDA 构建的 llama-cpp-python**，否则 try/except 降级 False |
| `n_batch` | 512（默认） | `2048` | prefill 提速明显，只对prompt摄取阶段生效，纯赚 |
| `n_ubatch` | 未设 | `512` | 新版参数；老版本不支持 → `TypeError` 兜住再重试一次 |
| `type_k/type_v` | f16 | `GGML_TYPE_Q8_0` | 见 P0。与 flash_attn 的组合需在目标机实测二选一 |
| `use_mmap` | True | 保持 True | 关掉会把整个 gguf 读进 RAM |
| `use_mlock` | False | 保持 False | Windows 上 True 会锁页甚至失败 |
| `n_threads` | 默认 | 显式=物理核数 | 别给超线程数，抢 H3 的 CPU |
| `n_threads_batch` | 默认 | = 物理核数 | prefill 并行度 |

**按需加载 mmproj**：无图任务（纯文本扩写）当前也会挂上位 handler。
改成"本次调用无图就不带 mmproj"，省 1GB 显存 + 省视觉塔 prefill。

## 五、P3｜分级路由（唯一能带来数量级提升的）

按显存算：

- 27B Q4 ≈ 19GB → ~25 tok/s → 输出 1000 汉字 ≈ 40s
- **8B Q4 ≈ 5.5GB → ~70–100 tok/s → 同样输出 ≈ 10–12s**，且常驻毫不影响 H3

结合项目里的分工口径：**AI 扩写（发散）= 内容生产，用大模型；提示词优化（格式编译）= 机械转换，8B 足够**。
这条落地只需要一个 router 字段（`local_model_small` / `local_model_large`），改动面比 P1 小，收益比 P1 大。

**如果目标是 30B 级**：优先 **MoE 型号**（如 Qwen3-VL-30B-A3B）。它和 dense 27B 同体积差重量级，
但每 token 只激活 ~3B 参数 → 搬运量小 3 倍以上 → tok/s 显著更高。前提是**所有专家都在 GPU 上**，
绝不能用 `--n-cpu-moe` 那种把冷专家甩给 CPU 的做法（3090 上会反噬）。

## 六、P4｜合并调用（可选）

一次 UI 操作若触发多段优化，现在会重复"加载 + prefill 系统提示 + 规则文件" N 遍。
合并成"一次调用处理多段"能把第 2、3 笔开销摊薄。改动量大（提示词结构要重写、失败粒度变粗），
建议**排在 P0/P3 落地并实测之后再评估**。

小替代：至少保证"扩写 → 优化"两连步复用同一个句柄（P1 天然覆盖）。

## 七、Transformers 路径（若不用 GGUF）

- `attn_implementation="sdpa"`：torch 自带，**不需要装 flash-attn**（Windows 上编译地狱）。
- `dtype=bfloat16`：**3090 是 Ampere，原生支持 bf16**；现有代码写死 `float16`，
  多模态 VL 模型在 fp16 下容易溢出出乱码。
- **`device_map=device` 要改掉**：传字符串需要 `accelerate`，而 embeded 环境里没有这个包 →
  当前写法在某些环境会直接报错。改成 `.to(torch.device(device))` 更稳。
- **不要** `torch.compile` / CUDA graph：动态 shape + 一次性短任务，编译时间远超收益。

## 八、明确不做（不符合"保守 + 只在 ComfyUI 现成环境里"）

| 思路 | 不做的理由 |
|------|-----------|
| vLLM / SGLang / TRT-LLM | 要另起进程装大件，脱离 ComfyUI 环境；且 GPU 要和 H3 抢 |
| fp8 KV / 原生 FP8 | **3090 是 Ampere，没有 FP8 单元**，那是 40 系以上的东西 |
| 降到 Q3/Q2 量化 | 省的是带宽但掉的是质量，属于"换命"不是"加速" |
| Q5/Q6 量化 | 更大更慢，别为"质量更好"误操作 |
| 投机解码（draft model） | llama-cpp-python 支持不稳定，且要额外小模型常驻显存 |
| exllama / llama.cpp 之外的内核 | 不支持 Qwen3-VL 视觉塔，且与 ComfyUI 生态不通 |

## 九、待你确认的四件事

1. **目标机实装版本**：llama-cpp-python 是 CUDA 构件吗（能吃到 `n_gpu_layers`）？版本号多少（决定 `n_ubatch` / `type_k` / Qwen3-VL 支持）？
2. **具体型号**：27B 是 dense 还是 30B-A3B MoE？是否有 8B 可用？
3. **是否接受 P1**（句柄常驻 + 钩子）——这是唯一改生命周期的改动，也是唯一有风险的项。
4. **H3 占用的显存**：跑 H3 时 LLM 必须让它，**两者不同时驻留**这个前提你认不认可。
