# 桥锚相位对齐：调查与实施

> 2026-10-24 ｜ 起因：「长链越跑越偏色，能否用 LUT 每段调一次配色」
> 结论：偏色是另一条线（见 §4）；本次真正修掉的是**桥锚抽帧的 token 相位错位**。

## 0. 结论摘要

| 问题 | 结论 |
| --- | --- |
| 标准 3D LUT 能否作用于 latent | **不能**（定义域/语义都不匹配），只能用线性化近似 |
| 每段结束用 LUT 调色能否治累积偏色 | **不能**（桥锚是 latent 直切片，像素域调色不改变下段起点） |
| 是否存在累积偏色 | **前提已失效**：`color_match` 证伪报告依赖的「接缝精修」已被删除（§4） |
| 桥锚抽帧是否错位 | **是，且默认配置 100% 错位**（§6） |
| 已修 | `end_t` 相位吸附 + `ctx=1` 裁头量（§9） |
| 未修 | settling 燃烧帧、正文首 token 相位、LUT 类后处理（§10） |

## 1. 起点：LUT 能否解决长链偏色

用户设想：每段生成结束后用 LUT 把配色拉回参考，阻止长链偏色累积。

这个设想有三层问题：

1. **LUT 无法作用于 latent**（§2），只能作用于已解码的像素。
2. 桥锚取的是**上一段采样输出的 latent 直切片**（`_tail_keyframe`），像素域调色**不改变 latent 一个数** → 下一段仍从漂移的 latent 出发。
3. 每段单独拟合 LUT 参数，校正量本身会变成新的段间跳变源（连续漂移换成离散台阶）。

**LUT 可以是执行器，不能是机制。**

## 2. LUT 与 latent 的关系

| 维度 | 3D LUT 的定义域 | H3 latent |
| --- | --- | --- |
| 通道语义 | RGB 三通道 | **24 通道**（`nodes.py:199`、upscaler `in_channels=24`），纹理/结构混合编码 |
| 值域 | 归一化 [0,1]³ | 零均值连续分布，跨度约 ±6，**不是有界立方体** |
| 分辨率 | 逐像素 | 空间压缩（一个 token ≈ 8×8/16×16 像素块） |

LUT 本质是「在归一化立方体上逐点查表 + 三线性插值」。latent 既不在那个立方体里，也没有那三个轴，**没有定义域可索引**。

能搬过去的只有「线性化 LUT」：

| 形式 | 表达 | 自由度 | 可行性 |
| --- | --- | --- | --- |
| 3D LUT（33³） | 逐点查表 | 35937 | ❌ 定义域不成立 |
| 全仿射 | `z' = Wz + b`（24×24） | 600 | ⚠️ 可做，但等同 Director 试过的「全 RGB 混合」→ 重影/花屏风险 |
| 对角仿射 | `z'_c = a_c·z_c + b_c` | 48 | ✅ 最稳 |
| 像素域 LUT + 重编码 | decode→LUT→encode | 35937 | ⚠️ 可行但贵（VAE 编码 362 帧上限、5GB 权重） |

## 3. 对照：Director 的低频残差调色

`AIMixer/ComfyUI_MiniMaxH3_Director`（下称 Director）是平行实现，同源（官方 `minimax_keyframes` 协议）。

它的桥锚 `h3_motion_context.py` **零数值调整**（原样注入），色彩相关只有 `segment_continuity.py` 的两处：

```python
# 低频残差：out = src + w * (blur(guide) - blur(src))
CONTINUITY_EXPORT_GRADE_FRAMES = 12
CONTINUITY_EXPORT_GRADE_WEIGHT = 0.70
CONTINUITY_EXPORT_GRADE_BLUR   = 64

# 加性亮度：Y 从 guide[-1] 线性过渡到 body[12]，每帧限幅
CONTINUITY_SEAM_ADD_LUMA_FRAMES = 12
CONTINUITY_SEAM_ADD_LUMA_MAX    = 0.10
CONTINUITY_OPENING_EXPOSURE_SPIKE = 0.008
```

**默认关**：`DirectorPlan.continuity_enabled = False`，需 UI 手动开「段间引导」。且 12+ 个 continuity 机制被置 0，只剩这两个生效。

负面清单（勿复活）：全 RGB lerp → 重影；乘性增益 → 画面花；序列交叉淡化 → 拖影+一顿一顿；mask ramp → 去噪不足花屏；双向混合 → 把下段姿态画进上段结尾。

**关键局限**：它只治接缝瞬态，不治累积（`guide` 取的是未被 grade 改过的段尾，校正无法闭环）。

## 4. 关键发现：证伪报告的前提已失效

`docs/color_match_falsification.md`（2026-09-02）结论是「段间色彩漂移没有物理来源，color_match 砍掉」。

它的核心论据之一是：

> 接缝处理 | 默认「潜空间精修」：缝两侧出自**同一次去噪** → 缝两侧颜色由同一次采样统一

但当前代码（`nodes.py:2934`）：

> 潜空间精修 / smoothstep 像素混合 / 智能切镜**已剔除**，不再有 seam profile。

**前提被删，结论需重新评估。** 报告写于 9-02，代码后来变了。

另一处盲区：`seam_doctor` 判据是「接缝前后各 8 帧窗口 ΔE ≥ 0.05」。若每段只漂 +0.02，**任何单条缝都低于阈值**，但 20 段累积 +0.4。**微分指标测不出积分现象。**

→ 要抓累积漂移，须比较「第 1 段 vs 第 N 段」的绝对色差，并看 ΔE 序列的符号是否单调。

## 5. 帧网格：为什么 22 帧不是 22 帧

H3 的 VAE 时序压缩**不等距**（`grid.py:10`）：

```python
FRAME_PER_TOKEN = (1, 4, 4, 4, 4)   # 首 token 1 帧，其后每个 4 帧，5 个一周期
```

- 5 token = 17 帧 = 一个周期
- 22 帧 = 7 token（`1+4+4+4+4+1+4`）
- `video_latent_t(17k+5) = 5k+2`、`latent_t_to_frames(5k+2) = 17k+5`（精确往返）

**token 的承载帧数由「距段首多远」决定**：`FRAME_PER_TOKEN[序号 % 5]`。

## 6. 相位错位：实测与根因

### 现象

默认配置（ctx=22、段长 124）下，从上一段抽 7 个 token 作为桥锚：

```
上一段 token 37–43 的帧数：4,4,4,1,4,4,4 = 25 帧
本段 token 0–6  的帧数：1,4,4,4,4,1,4 = 22 帧
```

**总数 25 vs 22，且逐 token 错位**（`4→1`、`1→4`）：上一段「装 4 帧的潜表示」被塞进本段「装 1 帧的位置」。

### 根因

```
锚定区 token 数 = video_latent_t(17k+5) = 5k+2 ≡ 2 (mod 5)
正文 token 数   = video_latent_t(17b+5) = 5b+2 ≡ 2 (mod 5)
                                  总和 ≡ 4 (mod 5)  ← 需要 ≡2 才对
```

**两个 17k+5 相加不再是 17k+5**（mod 17 得 10）。于是起点 = `总和 - vt` 落在周期中间（相位 2）。

### 实测（纯逻辑复现，段长 96–362 全扫）

| ctx | 裁头正确率 | 逐 token 匹配率 |
| --- | --- | --- |
| 1 | 0% | 0% |
| 5 / 22 / 39 / 56 | 100% | **0%** |

15 档实际段长（17k+5）**无一例外**：`end_t%5 = 4`、相位 2、覆盖 25。

### 为什么必须逐 token 匹配

本段 token 0 **恒为 1 帧**（`FRAME_PER_TOKEN[0]`）。所以抽来的第一个 token 也必须是 1 帧的，否则语义错位。

- 起点相位 0 → 首 token 1 帧 ✓
- 起点相位 4 → 首 token 4 帧 ✗（总数可能也是 22，但结构全错）

**「总数对」不等于「结构对」。** 曾误判为「相位 0 与相位 4 等价」，实测逐 token 后推翻。

## 7. Director 是怎么对齐的

Director 的做法是**在生成帧数这一层向上 align**：

```python
lock_px  = 22                      # 锚定区
settling = 12                      # 燃烧帧（导出时裁掉）
body     = 124                     # 用户可见长度
lookahead= 8                       # 网格覆盖余量
raw      = 22 + 12 + 124 + 8 = 166
sample   = align_up(166) = 175     # ← 向上补到 17k+5
trim     = lock_px + settling = 34 # 解码后裁掉
```

核算：

```
175 帧 → token 52，52 % 5 = 2 ✓
起点 = 52 - 7 = 45，45 % 5 = 0 ✓
抽的序列 = [1,4,4,4,4,1,4] = 22，本段占位同 → 逐 token 匹配 ✓
导出 = 175 - 34 = 141，再裁回 124（keep_tail=False）
```

**但 `align_up` 本身不是对齐手段。** 真正起对齐作用的是下面这段枚举：

```python
# _phase_aligned_tail_start：只从周期边界枚举，末端不得超过 end_frame
for start in range(0, total_steps - n_steps + 1, 5):
    end_px = pixel_frames_for_latent_t(start) + pixel_frames_for_latent_t(n_steps)
    if end_px <= end_frame and end_px >= best_end_px:
        best_start = start
```

- `end_frame = trim + visible = 34 + 124 = 158`（**导出末端**，不含 lookahead/align 余量）
- 在 total 范围内枚举「起点 % 5 == 0」的窗口，取末端最靠近 158 的那个

实测（vt=7、end_frame=158）：

| total_token | 总帧 | 选中起点 | 起点帧 | pin 末端 | gap | 相位 |
| --- | --- | --- | --- | --- | --- | --- |
| 47 | 158 | 40 | 136 | 158 | 0 | 0 |
| 49 | 166 | 40 | 136 | 158 | 0 | 0 |
| 52 | 175 | 40 | 136 | 158 | 0 | 0 |

**只要 total ≥ 47，pin 结果与 total 完全无关。**

### 7.1 align_up 到 175 的实际作用

| 目的 | 需要 align 吗 |
| --- | --- |
| pin 相位对齐 | ❌ 不需要（枚举自己保证） |
| 避免 VAE padding | ❌ 不需要（166 是 token 49 的边界，可精确往返） |
| lookahead 诱饵加长（8 → 17） | ✅ 顺带 |
| `keep_tail=True` 导出更长（132 → 141） | ✅ 顺带 |

**align 对「对齐」本身没有贡献**，它是 `round up to 17k+5` 的机械调用，顺带把尾部诱饵拉长了一倍。

> ⚠️ 本节早期版本写「靠总和落 17k+5 自动得到 ≡2」——**错**。total=49（166 帧，token ≡4）同样能对齐，因为起点由枚举决定，与 total 无关。

### 7.2 pin 取哪部分帧

```
序列:  [lock 22][settling 12][body 124][lookahead 8 + align 9]
帧号:   0       22          34        158                    175
        └─ 裁掉 ─┘└── 导出 ──┘└── 裁掉，不进 pin ──┘
                                    ↑ pin 取帧 136–158（导出内容的最后 22 帧）
```

- **lookahead/align 那 17 帧不进入 pin**，它们的唯一作用是「让模型以为还没到终点」，从而不在尾部收尾
- 尾部诱饵失效的后果：段尾冻结 → 下一段 lock 是冻结内容 → 卡顿沿链传播

### 7.3 三种帧的角色

| | 来源 | 参与前向 | 被更新 | 作用 |
| --- | --- | --- | --- | --- |
| `lock` | 上一段 latent 尾部切片 | ✅ | ❌（每步按回原值） | 提供「确定的过去」 |
| `settling` | 本段自由生成 | ✅ | ✅ | 吸收段首 hold→pop（导出裁掉） |
| `body` | 本段自由生成 | ✅ | ✅ | 观众看到的内容 |
| `lookahead`+align | 本段自由生成 | ✅ | ✅ | 骗模型不提前收尾（导出裁掉） |

> ⚠️ `lock` 常被误称「不进采样」。准确说法是**不被更新**——它仍参与每步前向（attention 必须看到它），所以序列变长时单步时间照样上升。

## 8. 本项目为什么和它不同

| | Director | 本项目（本次修复前） |
| --- | --- | --- |
| 对齐机制 | **枚举周期边界起点**（`_phase_aligned_tail_start`） | **无**（直接 `end_t - vt`） |
| 末端约束 | `end_frame = trim + body`，可提前 → 产生 gap → 裁上一段尾部 | `end = end_t`（导出末端）→ gap ≡ 0 |
| 相位保证 | 枚举时强制 `start % 5 == 0` | 无 |
| 结果 | 相位 0 | 相位 2 |

**根本差异是「以哪一端为基准」：**

- **Director 以起点为基准**：只从周期边界取窗口 → 末端被动、可能提前 → 需要 `prev_export_trim_tail` 裁上一段补 gap
- **本项目以末端为基准**：`end` 精确压在导出末端 → gap ≡ 0，但起点被动 → 相位随机（实测 100% 错位）

两者各解一半。本次修复取第三条路：**末端主动吸附到「能产生周期边界起点」的位置**，同时保住 gap ≡ 0 —— 既不裁上一段，也不需要枚举：

```python
end_t = frames_to_latent_t(skip_f + vis_len, up=...)
end_t = grid.align_phase_down(end_t)          # 让 end_t ≡ 2 (mod 5)
vis_len = latent_t_to_frames(end_t) - skip_f
```

等价于 Director 的 `_phase_aligned_tail_start`，但只需一次减法，不用枚举，也不产生 gap。

### 两个可选方向

| | 向下吸附（已实施） | 学 Director 向上补 |
| --- | --- | --- |
| 做法 | `end_t → ≡2 (mod 5)`，`vis_len` 随之减少 | 生成 `align_up(skip_f+vis_len)`，多出的裁掉 |
| 生成量 | 141（比 146 少 5） | 158（比 146 多 12） |
| 导出量 | **119**（比用户设 124 少 5） | **136**（比用户设多 12） |
| 成本 | 略降 | +8% 生成 |
| 优点 | 实现最小，不动生成链 | 不减少用户要的帧数 |

已实施向下吸附的理由：改动只在一处（`_decode_crop`），不动 `_snap_seconds`/前端/`refvideo.TRAINED_MAX_FRAMES`，且实际时长（4.96s）比设定 5s 只差 0.04s。

若后续认为「不能少给帧」更重要，可改为向上补 —— 但那需要改生成帧数（`bridge_extra_frames`），爆炸半径更大。

## 11. 一页速览（给未来的自己）

**一句话**：桥锚抽 7 个 token，但 token 的容量由「距段首多远」决定，所以起点相位错了 → 抽来 25 帧塞进 22 帧位置 → 逐 token 语义错位。修法是让末端 token 数 ≡2 (mod 5)。

**三个必须记住的数字**

- `FRAME_PER_TOKEN = (1,4,4,4,4)`：5 token = 17 帧 = 一个周期
- 锚定区 token 数恒 ≡2（`video_latent_t(17k+5) = 5k+2`）
- 所以 `end_t` 必须 ≡2 (mod 5)，起点才 ≡0

**五个踩过的坑**

1. **「总数对」≠「结构对」**：25 vs 22 是错位，22 vs 22 也可能逐 token 错位（相位 4 那种）
2. **「lock 不进采样」≠「不花算力」**：lock 不被更新，但参与前向；序列变长照样变慢
3. **`align_up` 不是对齐手段**：`_phase_aligned_tail_start` 才是；total ≥ 47 之后 align 对 pin 无影响
4. **段长吸附到 17k+5 不保证相位**：需要落网格的是「锚定区 + 正文」的**总和**，不是段长本身
5. **`seam_doctor` 的 ΔE 是微分指标**：抓不到每段 +0.02 的慢漂移，要看 ΔE 序列的符号是否单调

**没做的两件事**

- `settling` 12 帧：段首不卡（+10% 成本）
- `lookahead` 17 帧：段尾不冻结（+12% 成本）

**判断顺序**：先开「桥帧门控 = 标注」看尾部实际打分，再决定要不要加——别先花成本。
