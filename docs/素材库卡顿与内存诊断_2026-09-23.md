# 素材库卡顿 / 内存上涨 诊断（2026-09-23）

输入：`D:/qq文件/Diagnostics-1790086234.log`（本机 Windows）+ 用户反馈
「把所有资产图传进素材库后操作变卡、内存变多、重新进 ComfyUI 加载变慢」。

---

## 1. 诊断日志先说了什么（本机环境）

| 项 | 值 |
|---|---|
| 平台 | Windows 10，ComfyUI **0.37.0**，comfy_aimdo 0.5.5，comfy_kitchen 0.2.35 |
| GPU | RTX 4070 **12 GB**（另有一张 AMD Radeon 12 GB，未被使用） |
| 内存 | **32 GB 总量，可用只剩 5 GB** ← 直接对上「内存占用变多」 |
| Pagefile | 36 GB，已用掉一半（空闲 18 GB）→ 已经在往磁盘换页 |
| 插件 | `ComfyUI-minimaxH3-SequenceForge-anchor-studio2`（**旧版**） |
| 模型 | `minimax_h3_hybrid_fl2va_ref2va_b25-49-int8` 19.5 GB + TE 25.3 GB |

三条与本任务相关的观察：

1. **`_seg_end_img` UnboundLocalError** —— 这是 `ab98332` 已经修掉的 bug，
   说明这台机器上的插件**版本落后于工作区**。先更新插件再谈优化。
2. `[H3性能] 显存 12.0GB · 内存 31GB · R_v 1.66 · R_m 2.16` → 12 GB 卡跑 19.5 GB 模型，
   **每步要重读 8.9 GB（46% 的权重）**。这是本机跑 H3 慢的结构性原因，与素材库无关。
3. `落盘守卫：⚠ … 可用内存 5GB + swap 18/36GB < 需求 81GB` → critical。
   Windows 有 pagefile 不会 OOM kill，但会把采样拖到分钟级。

顺带一条本机可调的：
- 配置里 **`Upcast Attention: True`** —— 12 GB 卡上建议关（强制 upcast 多吃显存、且拖慢）。
  已做成**节点端性能设置的开关**（本轮实现），不用改启动参数。

关于另外两条常见建议，本插件**不采用**：
- `--vram-headroom 1`：0.35 把显存吃到接近 100% 是官方有意拉高 H3 利用率，
  预留换来的代价是权重缓存变小、每步多重读权重 —— **有好有坏**，交给节点端按实测余量腾挪，
  并在性能设置里给用户开关，不出启动参数建议。
- TE 换 nvfp4 AWQ：非 50 系显卡上 nvfp4 没有硬件加速，且 int8 质量略好，
  本机沿用 int8（25.3 GB）是对的，不作为优化项。

## 2. 素材库卡顿的三层根因（都有实测数字）

### 根因 A · 每张缩略图都要重建一遍全量索引（O(N²)）

`routes.py` 的 `lib_thumb` / `lib_raw` / `lib_item` 都走 `_find_item()`，
而 `_find_item` 调的是 `_indexed()`，那条管线每次都要跑：

```
read_project（磁盘读） → build_index → apply_aliases → apply_roles
→ compute_refs → apply_meta（两份 sidecar 磁盘读）
```

素材库一页 60 张缩略图 = **60 次全量遍历**。合成库实测（一页 60 张）：

| 条目数 | 全量管线 | 快路径 | 提速 |
|---|---|---|---|
| 60 | 30.9 ms | 2.8 ms | 10.9× |
| 200 | 58.3 ms | 5.8 ms | 10.0× |
| 600 | 154.8 ms | 15.6 ms | 9.9× |
| 1200 | 315.2 ms | 29.4 ms | 10.7× |

雪上加霜的是 `_INDEX_TTL = 3.0`（3 秒硬过期）。缩略图请求一旦拖过 3 秒，
每次都触发全量 `os.walk` + manifest 解析：

| 条目数 | 60 次全量重建（TTL 击穿） |
|---|---|
| 200 | 328 ms |
| 600 | 875 ms |
| 1200 | 1895 ms |

**这就是「操作会很卡」**：素材越多，光翻一页的 Python 开销就从几十毫秒涨到近 2 秒。

### 根因 B · 缩略图生成要把整张大图全解码（内存尖峰）

`library.make_thumb` 原本是 `Image.open → convert("RGB") → thumbnail((256,256))`，
即**先把 1200 万像素完整解码成位图，再缩到 256px**。实测峰值（后台线程采样 RSS）：

| 源图 | 改前峰值 | 改后峰值 |
|---|---|---|
| 6000×4000 JPEG（21.5 MB） | **193.1 MB** | **14.0 MB**（−93%） |
| 4000×3000 JPEG（10.7 MB） | 48.4 MB | 3.0 MB |
| 6000×4000 PNG（72.1 MB） | 96.3 MB | 96.3 MB（PNG 不支持 draft，靠像素上限挡） |

关键：**Python 的分配器不会把释放的大块及时还给 OS**，这种尖峰反复发生会让
RSS 阶梯式涨上去并停在高位。**这就是「内存占用会变多」的后端那一半**——
32 GB 机器可用只剩 5 GB 就是这么来的。

### 根因 C · 前端瓦片只增不减（浏览器内存）

`h3_library.js` 的「加载更多」是 **append 模式**（`S.items.concat(...)`），
而缩略图一旦加载就 `io.unobserve(d)` 永久保留。翻十页 = 600 张解码位图常驻
（256px 缩略图约 260 KB/张 ≈ 150 MB，视频 `<video>` 还要拖着已缓冲的原文件）。
**这是「内存占用会变多」的前端那一半。**

## 3. 已做的修复（822 测试全过）

| # | 位置 | 改动 | 收益 |
|---|---|---|---|
| A | `library.py` 新增 `find_by_id()` | 按 id 取一条的快路径，绕开 apply_* 全管线与两次 sidecar 磁盘读 | 一页缩略图 **~10×** 提速 |
| A | `routes.py` `lib_thumb` / `lib_raw` | 改用 `find_by_id`（`lib_item` 仍走全管线——它需要 rating/tags/refs） | 同上 |
| B | `library.make_thumb` | 加 `im.draft("RGB", (size*2, size*2))` + `THUMB_MAX_PIXELS = 40_000_000` 守卫 | JPEG 峰值 **−93%**；超大 PNG 直接跳过（前端回落类型图标） |
| C | `web/h3_library.js` `renderGrid` | IntersectionObserver 改双向：出视野就摘掉 `img`/`video`，加 `thumbFail` 防重复重试 | 常驻解码位图从 O(已加载页数) 降到 O(视野内) |

**为什么 A 是安全的**：`apply_aliases` / `apply_roles` / `compute_refs` /
`apply_meta` 只改 `name` / `roles` / `refs` / `rating` / `tags`，
而 `resolve_item_path` 只看 `scope` / `file` / `linked`——这三个字段由
`scan_scope` 定死，不经 apply_* 。所以缩略图与原图走快路径与走全管线等价。

## 4. 还没做的（按性价比排）

| # | 措施 | 收益 | 风险 |
|---|---|---|---|
| 1 | **缩略图入库时生成**，而不是首次浏览时才生成 | 根因 B 彻底消失；首次浏览零解码 | 低；`register_content` / `library_upload` 里顺手调 `make_thumb` |
| 2 | **索引缓存改成指纹失效**（目录 mtime + 文件数），替掉 3 秒硬 TTL | 消灭 1895 ms 的 TTL 击穿 | 中；指纹算错会导致新上传的素材不显示，需谨慎 |
| 3 | `find_by_id` 再进化成 id→item 字典缓存 | 从 O(N) 降到 O(1) | 低；要跟着 `invalidate()` 一起失效 |
| 4 | **`_indexed()` 里的 `read_project` 与两份 sidecar 也缓存** | `lib_list` 每次少 3 次磁盘读 | 低 |
| 5 | 前端改虚拟滚动，或给 `S.items` 设上限 | 根因 C 的彻底解 | 中；交互会变 |
| 6 | 视频瓦片用服务端首帧缩略图（PyAV 抽帧），别用 `<video src=原文件>` | 视频多时收益最大 | 中；要接 PyAV 抽帧 |
| 7 | `Upcast Attention` 开关接入节点端（已在性能设置实现，见 §3） | 12 GB 卡上省显存 | 低 |
