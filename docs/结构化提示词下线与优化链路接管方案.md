# 结构化提示词下线方案（前端导演台 + 后端实现）

> 目标：彻底移除结构化提示词（prompt_v2 / 逐镜表单），**保留并强化 AI 提示词优化**，
> 让原本只能靠结构化表单做的编辑，改由「AI 优化 + 规则注入 + 确定性校验」承接。

---

## 0. 一句话结论

**结构化是纯旁路，实跑链路完全不依赖它。**

正文（`ds.prompts[idx]` → `seg["prompt"]`）始终是唯一真相，实跑只读正文。
结构化弹窗做的事情是「把正文解析成字段 → 用户改字段 → 编译回正文」，是个**旁路编辑器**。
删掉它不会动到生成链路的任何一环；AI 优化的落点就是「产出官方格式正文 → 写回段卡框」。

---

## 1. 举证：为什么下线是安全的

### 1.1 实跑对 `prompts.py` 的依赖只有 3 个符号

```
nodes.py:46   from . import prompts as _P
nodes.py:47   from .prompts import L2VA_HEAD, FL2VA_HEAD
nodes.py:1464 _end_s = _P.frames_to_seconds(seg_lengths[-1])
nodes.py:1466 L2VA_HEAD.format(shot=_last_shot, t=_end_s) …
```

其余全部是段卡预览（`/h3chain/compile`）与存档归一化在用，**不进生成链路**。

### 1.2 实跑有自己的一套组装器，与 prompt_v2 无关

`nodes.py:731 _compose_official()` 是**旧五字段组装器**（`scene_prompt` / `character_prompt` /
`prompt` / `soundscape` / `music`），逻辑：

| 情况 | 行为 |
| --- | --- |
| 正文含官方字段头（`_OFFICIAL_FIELD_RE`，`nodes.py:719`） | **原样直通**，不包装、不注入任何东西 |
| 否则 | 组装 `integrated_multimodal_description: [Shot 1] {场景}。{角色}。{正文}` |
| 正文无 `<d>` 且含 `「…」` | `_wrap_dialogue` 自动转 `<d>[中文] …</d>`（`nodes.py:723`） |

→ **用户（或 AI 优化）只要产出「官方三字段格式」的正文，实跑就是直通**。
这正是 AI 优化已经产出的形态（`build_system_prompt` 要求三字段/六节，`_validate_optimized`
按 `parse_override` 解析字段头）——链路天然对齐。

### 1.3 主框已是唯一真相（代码注释原文）

`h3_director.js:4554-4556`：

> 段卡版面要留给正文 —— 正文才是进模型的东西，结构化只是「同一份提示词的另一种写法（逐镜微调）」

### 1.4 ⚠ 一个必须处理的交互

`nodes.py:1440-1443 / 1462-1467` 的对齐指令注入都有 guard `not _OFFICIAL_FIELD_RE.search(...)`。

**含义**：正文带官方字段头 → 后端**不注入**对齐指令。所以走「官方格式直通」的段
（AI 优化产出必然是这种），对齐指令必须由优化链路自己带上，否则静默丢失。

→ 见 §3.2，这是本方案的核心新增项。

## 2. 能力盘点：哪些是「只能靠结构化做」的

按「LLM 能不能可靠接管」分三类。

| # | 能力 | 结构化实现（现状） | 类别 | 处置 |
| --- | --- | --- | --- | --- |
| 1 | 运镜类型（20 词枚举） | `prompts.CAMERA_MOVES` + `_CAMVERBS` 查表 | **A 写作** | 词表进规则文件 |
| 2 | 运镜幅度 / 速度 | `camera_amplitude` small/large、`camera_speed` slow/fast | **A 写作** | 同上（`with small amplitude` / `at slow speed`） |
| 3 | 屏显文字 | `screen_texts[]` 独立数组 → 英文双引号 | **A 写作** | 判据进规则文件 + 语义校验 |
| 4 | 对白结构化 | `dialogues[]`（speaker/language/delivery/voiceover） | **A 写作** | 规则已有 §2；补 voiceover 嘴唇闭合细节 |
| 5 | 多镜时间戳 | `format_ts(start_seconds)` → `[Shot N] At MM:SS.mmm` | **A 写作** | 规则补格式；校验已有 |
| 6 | 单镜补 `One continuous shot with no cuts.` | `compose_description:361-366` 自动追加 | **A 写作** | 规则补一句 |
| 7 | Ref2VA 六段式组装 | `compose_reference`（含 summary 任务前缀、retention 标记） | **A 写作** | 规则已有 §5；补混合模式 |
| 8 | 混合模式（帧锚占 Picture 1/2） | `compose_reference:frame_anchors` | **A 写作** | `system_compile.md` 已有，需搬到被注入的规则文件 |
| 9 | **模式判定**（T2VA/I2VA/…/Ref2VA） | `detect_mode` 读 has_start/has_end/refs 状态 | **B 计算** | **不许 LLM 写**，后端保留 |
| 10 | **对齐指令 + 真实时长 S.SS** | `alignment_lines` + `frames_to_seconds` | **B 计算** | **不许 LLM 写**，后端注入 |
| 11 | `@素材名` → `<Picture k>` 压实 | `asset_store.compile_refs`（后端） | **C 已有** | 不动，与结构化无关 |
| 12 | 字段/镜头/时间戳校验 | `validate_compiled` | **C 已有** | 保留 |

**A 类（9 项）** = 写作任务，靠「规则文件补齐 + 语义校验」接管 —— LLM 做得好。
**B 类（2 项）** = 纯计算，LLM 做不可靠（尤其 #10 的 `S.SS` 与段长帧数强绑定）—— 必须留在后端。
**C 类（2 项）** = 本来就不依赖结构化。

### 3.2 ★ 新增：优化结果确定性收尾 `finalize_optimized(text, *, mode, seconds, frames)`

**这是「接管 B 类能力」的关键**。LLM 产出后、写回正文前，后端做 LLM 算不准的活：

1. **模式判定**：用 `detect_mode` 的口径（读 `has_start` / `has_end` / 段 refs）定 mode，
   **不采信 LLM 自己声明的**。
2. **对齐指令注入 / 纠正**：
   - I2VA / L2VA / FL2VA 段 → 用 `alignment_lines(mode, frames_to_seconds(frames), …)`
     生成整句，**放在正文最前 + 空行**。
   - 若 LLM 已写了对齐句 → 先用现成的 `_KF_RE` / `ALIGN_*` 正则剥掉再重写
     （杜绝「前端 5.00 / 后端 5.17」那类不一致，`frames_to_seconds` 是唯一换算）。
   - T2VA / Ref2VA → 剥掉，不生成。
3. **单镜补 `One continuous shot with no cuts.`**（原 `compose_description:361-366` 的语义，
   但只在单镜且正文确实没有时补）。
4. **时间戳规范化**：`[Shot N] At MM:SS.mmm` 递增、`[Shot 1]` 去时间戳、不超时长。

> 这 4 步全部是**已有函数的复用**，没有新算法。`frames` 从段长取（与实跑同源）。

### 3.3 校验升级：把语义校验接上（原 §2 分析的缺口）

现状：`_validate_optimized`（`optimizer.py:1553`）只接 `validate_compiled` ——
**只有结构类检查**（字段 / 镜头 / 时间戳 / 对齐句 / 音画分离）。

缺口：`tools/h3_prompt_expander/validate.py` 里那套**语义检查完全没接**。

**搬过来**（该文件 240–322 行只读最终文本 + duration，**不依赖 intent IR**）：

| 检查 | 位置 | 作用 |
| --- | --- | --- |
| `W_QUOTE_ZH` | `validate.py:288-293` | 中文被双引号包 + 前 60 字符无 `reading\|sign\|neon\|subtitle\|screen\|写着\|招牌` → 疑似对白烧成屏显字幕 |
| `W_DIALOG_QUOTED` | `:281-282` | 有 `(S1)` 但台词写在引号里 |
| `W_MOUTH_CONFLICT` | `:284-285` | 台词后紧跟吞咽/闭嘴 |
| `E_FREEZE` | `:308-309` | `nothing changes` / 全镜静止句 |
| `W_NEG_EN` | `:304-307` | 英文否定堆叠（含白名单） |
| `W_ABSTRACT` | `:296-300` | 裸抽象词 |
| `W_BEAT_DENSE` / `W_LENGTH` / `W_REF_LENGTH` | `:263-269`, `:228-238` | 节拍密度、长度密度（按时长缩放） |

唯一依赖 intent 的是 `E_QUOTE_LOST`（`:325-329`，需要 `must_keep_quotes`）——
**改为从用户原文现抽**：优化时把用户输入里的引号内容当场记下，产出后逐条比对。

目标形态：`prompts.validate_text(text, mode, seconds)` = 结构检查（现有）+ 语义检查（搬入），
`optimizer._validate_optimized` 改为调它。

## 7. 实施顺序与风险

**建议顺序（每步可独立验收）**

1. **规则文件补齐（§5）** —— 纯文本，零风险，先做先受益（即使后面不继续，AI 优化也已经变好）
2. **后端 `finalize_optimized` + 语义校验（§3.2 / §3.3）** —— 新增，不动存量，可单测
3. **前端删除（§4）+ 测试改写（§6）** —— 一起做完，避免中间态
4. **后端瘦身（§3.1 / §3.4）** —— 最后删，因为删了就要保证没有残留调用

**风险点**

| 风险 | 处置 |
| --- | --- |
| 漏删 `prompt_v2` 透存 → 老存档带残留字段 | 无害（只是数据冗余）；`clean_prompt` 删掉后旧存档的 `prompt_v2` 字段**不再被清洗但也不再被读取**，可留可清，建议保留不读 |
| 对齐指令静默丢失（§1.4） | 由 §3.2 第 2 条兜住；且 §3.3 的校验能检出（`E_ALIGN` 系） |
| 规范 skill 与站内规则分叉（§5.3） | 两份 md5 比对进 CI/自检清单 |
| 前端漏删导致死代码引用（如 `effV2Mode` 残留在某处） | 删后全量跑 `tests/js/*.js` + `make_anchor_preview` + `anchor_ui_smoke` |

### 10.2 顺带修掉的 4 个真 bug（非本次引入，是查证时暴露的）

1. **`E_OVERRIDE_PREAMBLE` 误判**：官方格式本来就是「对齐指令句 + 空行 + 三字段」，
   但 `validate_compiled` 的 override 分支把前置对齐句当废话报错。

3. **Ref2VA 规则文件字段集与代码矛盾**：`pick_rule_text` 注入的是**四字段**版

4. **`clean_prompt` 静默清空运镜**：`camera_move` 不在词表即 `= ""`，差一个字符就丢且无提示
   —— 「结构化 bug 太多」的高概率来源之一（随结构化一起下线）。
