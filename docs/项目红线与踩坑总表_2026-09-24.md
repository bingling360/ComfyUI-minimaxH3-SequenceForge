## 块交换 blockswap（2026-09-23 定论）

- **不是分块计算**，是 block 权重在 GPU/CPU 间搬。省的是**常驻显存**不是权重总量；画质逐位不变，
  代价**只在时间**。
- **★ 官方早就做了，本项目不自己写**：`comfy/ldm/minimax/model.py:751-765`
  （`make_prefetch_queue` + `prefetch_queue_pop(malloc_scope="block")`）、`model_base.py:250` 总闸、
  `model_patcher.py:1795` `is_dynamic()`。**三条理由**：① 一个算法只能有一个主人（与官方
  `partially_load`/vbar 抢同一批参数）；② 打坏 LoRA（HyperFlow 走 comfy patch 链，与
  `model_loaded_weight_memory` 脱节）；③ aimdo 下权重住 vbar，官方明禁外部 pin
  （`pin_weight_to_device` → RuntimeError）。
- 落地 = **3 个真旋钮**：`blocks_swap_on`（关 → **恢复 baseline**，不是保持上次值）、
  `blocks_to_swap`（→ `comfy_aimdo.control.set_simple_vram_headroom()`，真调 + **读回核验**，
  超显存一半会夹取）、`blocks_prefetch`（官方队列写死"提前 1 块"）。`non_blocking` **已删**
  （官方恒 True + 锁页是 aimdo 硬前提）。无 aimdo 时折成 `EXTRA_RESERVED_VRAM`。
- **★★ `simple_vram_headroom` 语义**（`comfy_aimdo/control.py:215`）：① 是**「simple budget 要保持
  空闲的字节数」**，进程级；与 `init_devices` 的 **per-device** `extra_vram_headroom` 是**两回事**
  （`--vram-headroom` 喂后者，`--reserve-vram` 喂前者）。② **设 < 256 MB 完全无效**（measured poll
  有编译期地板 `VRAM_HEADROOM`，取较大值）→ 设 0 / 0.1GB 实际仍是 0.25GB。③ **只驱逐 VBAR 页**；
  torch 分配**只计入、永不拒绝** → **救不了「激活本身太大」的 OOM**。④ **调低不自动回填** →
  「关掉开关」= 把预留设回 baseline，**不是立刻搬回权重**。
- **官方默认 headroom = 0.25 GB**；**官方没有块交换开关**（预取队列无条件在跑，官方 H3 节点也没有
  `blocks_to_swap`）。我们抬 headroom = 把「被动滞后驱逐」变「**主动提前驱逐**」。
- **★ 边际收益**：多腾出 = `min(N × UNET/50, 显存×0.5 − 0.25)`。20GB UNET：6GB→**2.4GB**(6 块)/
  16GB→**7.6GB**(19 块)/24GB→**11.6GB**(29 块)。**但不降低总占用**（腾出的立刻被 torch 分配吃掉，
  变的是**分配结构**）→ **本来跑得动时抬高是纯亏**，只有卡 OOM 边缘才净收益。代价上界 =
  块数 × 71ms × 采样步数。
- **两条纪律**：① **读接口不许改进程状态**（`perf_get` 也走 `apply_blockswap`，算不出目标就
  `return`，一次 `_set_*` 都不许调）；② **基线只读一次并缓存**。
- **PCIe 基准**（本机 3.0 x16，~11 GB/s）：搬 0.4GB 恒 **~36ms/向**（来回 71ms，与 token 无关）；
  **搬/算比** 2048→**9.81**、4096→2.77、8192→1.37、16384→0.69 → 短序列**纯亏**，≥16k 才追平。
  6GB 卡上块交换是**唯一活路**。**换卡/换 PCIe 代次必须重跑** `tools/bench_blockswap_pcie.py`。
- ⚠ 锁页内存是硬账：本机 pinned 实测 6.34GB；16GB 内存档约 13GB。
- ⚠ 探针坑：先 `ctl.init()` 再 `init_devices()`；`aimdo_enabled`/`CoreModelPatcher` **只有
  `main.py` 会设**，独立进程要手工复刻。守卫 `tools/check_blockswap.py`（31 条，真 aimdo）。

## 显存 / 性能工程

- 放大前向补 `no_grad`（**不要 `inference_mode`**，出块做原地操作会报错）；腾挪顺序恒
  **unload → gc → empty_cache**。
- **★ 阶段 0 真 bug**：`render_latent` 漏 `_vram`/`_rss` 形参 → **每次二采 TypeError**（埋点从没在
  真机跑通所以没暴露）。已补源码级守卫。
- **★ Windows 探测两坑**：ctypes 默认 restype 是 `c_int` → 句柄截成 32 位 →
  `GetProcessMemoryInfo` 静默返 0（须显式声明 restype/argtypes）；swap 余量应减 **AvailPhys**
  而非 TotalPhys（减错被 clamp 成 0，误报「swap 已满」）。
- **OOM 的下场是 SIGKILL** → `perf.emit()` 逐点 append+flush 到 `logs/h3_perf_probe.jsonl`；
  回读 `tools/perf_report.py`。⚠ 测试里别用 `Z:/` 当不可达路径（`os.path.isdir` 要 15 秒）。
- 三判据（`perf.py:319-355`）：**R_v = unet_gb ÷ (vram_total × 0.98)**、
  **R_m = (unet_gb + te_gb) ÷ ram_total_gb**、**R_d = disk_free_gb ÷ (unet_gb + te_gb)**。
  ⚠ R_m 分子是 **UNET+TE**、分母是内存**总量** —— 稳态容量判据，不是瞬时峰值。
- **★ 分块现状**：A FFN token ✅、B 注意力头 ✅（移植 KJ，带装前自测）、C 块交换 ✅、
  E 放大网络时序 ✅、F 精化时序 ✅、G 精化空间 tile ✅（2×2/3×3/4×4/2×1/1×2 + 羽化）、
  D VAE 解码 ⛔ **不做**（官方 `comfy/sd.py:1023-1057` 已在 tile 级做完：256px 空间 × 17 帧时序，
  `handles_tiling=True`，只按单块算显存）。
- **★ 放大网络「块间重叠帧」`upscale_overlap`**（`upscale_net.py:380-469`，2026-09-24 实测）：
  `overlap < tk`（时序卷积核宽，实测 5）会被夹回 → **填 0/1/3 与填 5 完全等价**。
  中间块实际前向 = **`chunk + 4×overlap` 帧**（写回区 `[seg_start-ov, seg_end+ov)`，输入区再各扩 ov）；
  融合带 2×ov，两侧线性权重互补成 1；首块左 / 末块右不 ramp。
  理论感受野半径 **26 帧**（12 个核宽 5 的 TemporalConv3D × 半径 2 + 首尾 3D conv 各 1）→
  严格等价需 **ov ≥ 13**。实测接缝误差（隔离 GroupNorm 后）：ov=5→5.0e-4、8→5.3e-6、
  **12→2.4e-7（归零）**。
  ⚠ **两个独立误差源，overlap 只修一个**：`nn.GroupNorm(32,C)` 在 **(C,T,H,W) 上跨帧求统计量** →
  分块后每块统计量不同，**overlap 修不了**（raw 组接缝误差 4.8e-3，ov 5→32 不降反微升）→ 默认
  ov=5 的接缝误差约 **9 成来自它**，只能靠加大 chunk。⚠ 首块 `F.pad(replicate)` 改了视频开头的边界
  条件（整段跑那里是 conv 的 zero pad）→ 误差集中在 **t=0 起 ov 帧**，ov 越大受影响帧数越多。
  耗时（T=107/chunk=32）：ov=5 → **+60.7%**、8 → +97%、12 → +145%、16 → +190%。
  ⚠ **前端文案的「+37%」是「冗余占比」口径**（65/172=37.8%），**实际耗时增加 60.7%**，易误读。
  **调大 overlap 是「更慢 + 更吃显存」**（块内帧数↑ → 激活峰值↑），削弱分块省显存的效果。
  **结论：保持 0（=5）；要调 8~12；>16 收益封顶且双重代价。** 探针
  `tools/bench_upscale_overlap.py`（隔离手法：**把 GroupNorm 统计量钉在整段值**，**不能换
  Identity** —— 随机权重下失去归一化会逐层放大到 1e8）。
- **★ 实例属性赋普通函数 ≠ 绑定方法**：`m.forward = plain` 会缺 self → 签名**不含 self**，用默认
  参数绑死 `def _fwd(x, ..., __n=eff, __sa=attn)`。`install_ff_chunking` 与
  `install_low_vram_attention` 同坑。

## ★ 采样输出恒在 CPU（2026-09-25 定论，踩过）

`comfy.sample.sample` 收尾那一行把结果
`.to(device=comfy.model_management.intermediate_device())`（`comfy/sample.py:83`），
而 `intermediate_device()` 在**没加 `--gpu-only`** 时**恒返回 CPU**
（`comfy/model_management.py:1267`）。本机 NORMAL_VRAM、无 `--gpu-only`，正是这一档。

**推论（拿采样输出做任何张量运算前必须搬设备）**：

- 只写 `.to(dtype)` **不搬设备** —— 分块融合的累加器是 `torch.zeros_like(_vid)`（cuda），
  于是 `acc + sh * wv` 第一次融合就
  `RuntimeError: Expected all tensors to be on the same device … cuda:0 and cpu!`。
  **精化时序分块 / 空间 tile 因此从上线起必崩**，段被降级为基础分辨率 → 成片回落 352p。
  统一走 `upscale._sampler_out_to(t, acc)`（= `.to(acc.device, acc.dtype)`）。
- 离线副本会掩盖它：`tools/check_refine_tile_fusion.py` 的 `_fuse` 是融合数学的**副本**，
  纯 CPU 下 acc 与 sh 同设备、永不触发。**副本必须复用真代码的 helper**，
  且已有用例 ⑧ 专测「sh 在 CPU」（无 CUDA 时 SKIP）。
- **取证口**：单段二采失败被 `nodes.py:3001` 吞成一行 report，**prompt 仍报 success**，
  `comfyui.log` 里既无 `Processing interrupted` 也无 `!!! Exception during processing !!!`。
  ComfyUI 还开着时直接读
  `curl -s "http://127.0.0.1:8188/history?max_items=8"` → `outputs["<节点id>"]["text"]`，
  那才是真错误原文。
